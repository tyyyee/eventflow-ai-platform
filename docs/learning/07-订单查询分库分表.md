# 订单历史查询分库分表

## 范围与路由

交易订单、库存、付款、退款仍使用原交易库本地事务。
历史读模型扩展为两个独立查询 MySQL 实例、共 32 个固定分片。
正整数 user_id 从登录态取得，不能由查询参数指定。

```text
shard = floorMod(user_id,32)
database = shard / 16
table = ux_order_read_<两位全局分片编号>
例如 user_id=10086 → shard=6 → history0.ux_order_read_06
例如 user_id=31 → shard=31 → history1.ux_order_read_31
```

逻辑表为 ux_order_history；数据库数和分片数不作为可随意调整的运行参数。
历史列表及计数必须携带 user_id；不提供无分片键的管理端搜索。
现有 UUID 保持不变。缺少 user_id 的订单号查询不进入分片接口。

## 实施约束

1. 源数据库不由 ShardingSphere 接管，不替换已有事务管理器。
2. 本地投影与跨库投影分别确认进度，目标写成功后才确认对应版本。
3. 回填前启用增量同步意图；ID 游标不代表提交顺序，新变更仍由持久任务覆盖。
4. 所有查询分片写入必须带 user_id 和版本；旧版本不得覆盖新状态。
5. 切换前完成回填和全量核对；查询保留最终一致语义。
6. 保留本地读模型以支持回退，不在目标失败时自动无限回源交易库。

本机环境脚本：backend/scripts/sharding-local.ps1。
随机凭据保存在项目 .local/sharding，不提交版本库。
为规避本机 MySQL 8.0.31 对中文配置路径的限制，实验数据文件默认位于系统临时目录中按项目路径哈希隔离的 qupiao-mysql-* 目录；停止实例不会删除数据。可通过 RuntimeRoot 指定持久英文路径。
迁移到其他机器时复用 DDL，导出/导入需要保留的数据，再校验与切换连接；不要求重新生成业务数据。合成压测数据可按固定参数单独重建。

## 同步与迁移协议

源表 ux_order_projection 保留 applied_revision 供原同库投影使用，另增加 replica_revision、重试时间、失败次数和错误码供跨库投影使用。V13 的生成列 replica_pending 与就绪索引用于筛选待同步版本。

同步在事务外读取源事实与版本，写目标后再按版本条件确认源进度。目标已提交但源未确认会重放；只有较高版本可以覆盖目标状态。远端调用不持有源库活动行锁。目标故障不会撤销交易，也不会阻断原本地投影。

回填使用持久 ID 游标、owner 租约及条件保存检查点。目标写后检查点未保存时允许重复回填。ID 不是提交顺序水位，回填期间的新增和状态变化继续由持久同步任务捕获。

核对覆盖用户归属、订单及请求 ID、活动、金额、状态、时间、版本及展示字段，并审计各物理表的 user_id 路由和总行数。缺行或字段不一致会提升源投影版本并重新排队。目标出现不可信的异常超前版本、错分片或多余行时禁止切换，需人工排查；不自动删除无法确认归属的数据。

## 本机验收与维护

在项目目录使用 PowerShell 运行：

```powershell
./backend/scripts/sharding-local.ps1 init
./backend/scripts/sharding-local.ps1 test
./backend/scripts/sharding-local.ps1 benchmark
node ./backend/scripts/sharding-report.mjs
```

init 不操作 3306 服务；会创建源实验库、两个查询库及独立基准库。test 运行正确性验收，benchmark 单独生成 10 万和 100 万条合成查询记录。不要将两种验收并行运行。

对实验源库进行离线维护：

```powershell
./backend/scripts/sharding-local.ps1 backfill
./backend/scripts/sharding-local.ps1 sync
./backend/scripts/sharding-local.ps1 verify
./backend/scripts/sharding-local.ps1 sharded
./backend/scripts/sharding-local.ps1 local
```

每次维护命令最多工作约 30 秒，未完成时再次运行，沿持久游标继续。先回填、同步并核对通过，才能切换到 SHARDED。切回 LOCAL 无需清空或重建数据。
这些命令通过本机忽略配置中的数据库凭据执行，审计 actor=0 表示离线维护；不启用实验 HTTP Bearer 鉴权。应用中的管理 API 继续沿用原管理员鉴权。本轮没有新增生产管理员账户体系。

默认构建不包含 ShardingSphere。启用需执行 `mvn -Psharding clean package`，并设置 HISTORY_REPLICA_ENABLED=true、HISTORY_URLS、HISTORY_DB_USER、HISTORY_DB_PASSWORD。源数据源仍按原 DATABASE_URL 等变量配置。切换 Maven profile 时使用 clean，避免保留上一次构建的可选类文件。sharding profile 中 H2 仅用于 ShardingSphere 内部元数据，不承载任何业务订单；该依赖会随分片运行包一起包含。

PowerShell 脚本需要 7.2+、JDK 17+、Maven 3.9+ 及本机 MySQL 二进制。脚本支持 JavaHome、Maven、MysqlHome 参数，不要求全局替换已有工具或数据库服务。

## 迁移到其他机器

迁移权威交易数据不需要重新生成订单。先切回 LOCAL，停用旧跨库同步及回填工作，再通过数据库备份恢复源库；对需要保留的查询库也可备份恢复。启动新源库后先保持 LOCAL，确认连接与路由，再进行同步、核对和切换。
若新查询库为空而保留了旧源库的进度，不得直接沿用旧 verified_at 或启动 SHARDED。先保持 LOCAL，若原回填未完成则完成剩余回填，再全量 verify；核对会重新排入缺失记录，sync 后再次完整 verify，通过后才切换。
实例 URL、分片数或映射改变不属于透明配置修改。停止旧工作者并重新核对是操作前提；本轮没有自动扩容、在线重分片或零停机迁移承诺。

## 容器部署

可选叠加文件 compose.history.yaml 为两个新查询实例挂载独立卷和初始化 SQL，并通过构建参数启用 sharding profile：

```bash
docker compose -f compose.yaml -f compose.history.yaml up -d --build
```

先设置独立 HISTORY_DB_PASSWORD。原 compose.yaml 不变，单独启动仍保持默认同库模式。
本机无 Docker，本轮只完成 YAML 和 DDL 一致性检查，未执行容器启动；真实验收使用本机 MySQL 8.0.31，容器声明的 8.4 不在本轮实测范围内。

## 结果解释

1 万条源历史订单用于断点回填、实时状态更新及完整核对。10 万和 100 万条记录写入独立基准 schema，仅用于三种查询布局比较，未灌入交易源库，也未计为真实下单吞吐。
基准为 JDBC 层 list+count 闭环查询，每模式并发上限 8、三轮、每轮 3 秒，固定用户分布及轮换顺序；不包含 HTTP 网络、Cookie 会话鉴权或实际入口控制查询。保留逐操作耗时并独立复算。短轮次和共享宿主机使其仅可作为本机观察。
单实例 buffer pool 128 MiB，对照双实例各 64 MiB；双实例每节点四条查询连接，同一热点用户仍只能访问其中一个节点。布局之间还包含 ShardingSphere 和连接管理差异，不能将全部差异解释为纯分片收益。
测试记录、批次标识和精简结果位于 docs/verification/2026-10-27-sharding；原始样本与失败日志位于本地 .local，不提交密钥或实验数据库文件。
