# 趣票：隔离环境中的完整业务联调

本轮在已有订单查询分库分表实现上补充真实 HTTP 验收。源码、数据和脚本仅属于趣票项目；不使用系统 3306 中的数据库。验收结果见[本轮记录](../verification/2026-10-27-full-integration/README.md)。

## 本机运行环境

| 服务 | 地址 | 用途 |
|---|---|---|
| MySQL 8.0.31 | 127.0.0.1:33307 | 隔离交易源库、本地 32 表读模型 |
| MySQL 8.0.31 | 127.0.0.1:33317、33318 | 两个历史查询实例，总计 32 张表 |
| Redis Windows 3.2.100 | 127.0.0.1:36380 | 本轮 Lua 预占、限流、缓存与关单索引 |
| Kafka 3.9.0 / KRaft | 127.0.0.1:39093 | 本轮持久化异步建单消息 |
| 后端 / JDK 17 | 127.0.0.1:38093 | Cookie 会话、交易、历史查询 HTTP |

本机没有 Docker。这里复用已安装的程序并为项目单独配置数据目录和监听端口；没有修改安装目录配置或系统服务。Compose 中 MySQL 8.4、Redis 7.4 和 Kafka 3.9.1 的容器组合仍需在具备 Docker 的环境单独验证。本机 Redis 版本仅用于这次兼容性验收，不据此替换 Compose 的版本。

随机密钥、会话和组件日志保存在忽略目录 `.local/integration`；数据库凭据沿用 `.local/sharding`。Kafka、Redis 的持久数据保存在带项目哈希的临时目录，MySQL 沿用分片实验目录。后续换机器仍可以备份恢复，无需重新生成交易数据。

## 启动和验收

先完成[分片环境初始化与构建](07-订单查询分库分表.md)。运行包必须使用 `sharding` profile 构建；本轮脚本需要 PowerShell 7.2+、JDK 17 以及本机 MySQL、Redis、Kafka 程序。

在项目根目录执行：

```powershell
./backend/scripts/integration-local.ps1 start
node backend/scripts/integration-http.mjs
./backend/scripts/integration-tests.ps1
node backend/scripts/integration-report.mjs
./backend/scripts/integration-local.ps1 status
```

脚本默认程序路径对应本机安装位置。更换安装位置可传入 `-JavaHome`、`-MysqlHome`、`-KafkaHome`、`-RedisHome`；跨机器复现时还需同步更新 HTTP 脚本的 `INTEGRATION_MYSQL` 环境变量，以及回归脚本的 Java/MySQL 参数。

HTTP 脚本会创建一组测试账户和活动，使用注册接口发放的 Cookie 与 CSRF token 完成客户操作。管理操作使用项目已有的实验 HMAC 管理令牌，因此此环境通过 `upgrade.benchmark=true` 启用实验入口，并且只绑定本机。该管理方式不是新增的生产管理员账户体系。模拟支付不涉及真实资金。

运行中会停止并恢复专属查询实例、Kafka、后端和 Redis，勿同时运行其他依赖这些实例的测试。脚本用真实的五分钟订单期限验证关单，完整执行至少需要五分钟。重复执行会创建新的独立批次，不清空已有数据；失败时尽力恢复组件并切回 LOCAL，日志仍需检查。

启动脚本不仅检查端口，还等待后端 readiness。为处理本机共享资源下的偶发启动失败，最多启动三次，并保留前次日志；没有放宽应用原有 Redis 300ms 超时。

## 验收内容和数据边界

- 登录、注销、CSRF、匿名及普通用户管理权限检查，跨账户订单访问和分片用户隔离。
- Redis Lua 预占、源库请求/Outbox、Kafka 消费建单、支付通知重复执行、取消及订单历史同步。
- 历史回填与完整字段核对，通过后切换 SHARDED；查询库中断时返回 503，源库管理入口可切回 LOCAL，交易继续，恢复后任务重试补齐。
- Kafka 中断时接受的持久请求，经后端停止、Kafka 恢复及后端重启后建单，权威订单只有一条。
- Redis 中断时拒绝新预占，历史查询仍可使用；恢复连接后继续执行。
- 自然五分钟关单、数据库与 Redis 票额回补、关单后模拟到账的退款，以及分片端最终状态可见。
- 登录后历史接口的三轮 LOCAL/SHARDED 对照，以及从源时间戳到分片 HTTP 首次可见的观测。

HTTP 测试使用少量真实接口创建的订单；8 个工作线程、17 个账户、每次请求后等待 25ms，每模式三轮，每轮 10 秒。它测量的是带真实会话和入口逻辑的端到端行为，包含刻意等待的完成请求/秒不代表最大吞吐。逐条核对结果，并独立复算原始耗时 CSV。

此前百万级合成记录的测试发生在独立基准 schema，是 JDBC 层三种布局对照；它与本轮 HTTP 数据规模不同。不得将两项测试拼接成“百万订单下接口达到某吞吐”的结论。

`integration-tests.ps1` 每次创建单独的回归 schema，使用 Redis DB13、独立 Kafka topic/group 和关单 key，启用原有外部中间件测试。不会向本轮业务源库灌入原有测试的并发和异常 fixture。

Redis 健康检查恢复，不代表每条已有业务连接同时恢复。恢复检查使用同一个请求键对 503 做有界重试，单独记录重连窗口内的 503 次数和首次成功耗时。故障恢复阶段的这些预期拒绝与稳定阶段 HTTP 对照的错误率分别记录。

## 收尾和复现记录

成功后读模式保留 LOCAL；组件保留运行，可用以下命令查看或停止新增进程：

```powershell
./backend/scripts/integration-local.ps1 status
./backend/scripts/integration-local.ps1 stop
```

`stop` 停止本脚本启动的后端、Kafka 和 Redis；三个 MySQL 实例继续由 `sharding-local.ps1 stop` 管理。后端与 Kafka 的停止方式也用于本轮进程中断实验，数据保留，不删除数据库或持久卷。

本轮没有重做浏览器 UI 验收、真实支付接入、容器部署或真实大模型效果评估。新增业务能力和简历表述以已验收事实为准。
