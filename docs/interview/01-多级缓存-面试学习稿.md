# 01—热门活动基础信息的多级缓存

## 对应的简历亮点

基于 Caffeine 和 Redis 实现多级缓存，结合 Bloom Filter 过滤无效 ID；软过期时短暂返回旧数据，通过分布式锁协调异步重建，Redis 异常时限制直接查询数据库的请求量。

截图中的性能数字另见第九节：当前文件中没有找到 13.85→10.85ms、4,204→5,396 req/s 的对应记录，不能将其当成本次已核实的结果。

## 一、先说业务问题：为什么加缓存

校园音乐节开票前后，很多学生会反复查看同一场活动的名称、介绍。这些信息读得多、改得少，没有必要每次都从 MySQL 查询。

当前代码沿用 `Shop`、`ux_shop` 等历史命名，页面业务已经是校园活动。这里讨论的是名称、介绍等基础信息；票档和交易库存由 `ux_activity` 等记录管理。缓存介绍与判断能否出票是两件事。

最直接的方案是：先查 Redis，没有再查 MySQL，并把查询结果存入 Redis。但还有四个问题：

| 问题 | 为什么会发生 | 我的处理 |
| --- | --- | --- |
| 热门信息仍反复访问 Redis | 每次都需要网络请求，并把 JSON 转回 Java 对象 | 增加 Caffeine 本地缓存 |
| 大量不存在的 ID 穿透缓存 | 每个新 ID 在缓存里都没有 | Bloom Filter 加短期空值缓存 |
| 热点缓存过期后集中查数据库 | 很多请求同时发现没有新缓存 | 软硬期限加互斥重建 |
| Redis 故障后数据库压力暴涨 | 原本命中缓存的请求都可能转向 MySQL | 熔断、限制查询速率和并发 |

## 二、几个组件各自负责什么

| 组件 | 通俗解释 | 在本项目中的作用 |
| --- | --- | --- |
| Caffeine | Java 程序自己内存里的缓存 | 保存近期访问的 Java 对象，减少 Redis 请求 |
| Redis | 多个后端共同访问的独立服务 | 保存共享缓存，以及重建锁等协调信息 |
| Bloom Filter | 占空间较小的存在性过滤器 | 辅助判断 ID 是否可能存在，不保存完整活动信息 |
| MySQL | 原始业务数据所在的数据库 | 没有可用缓存时查询，更新时以它为准 |

所以准确说法是“两级缓存加过滤与保护机制”。`Caffeine → Bloom Filter → Redis → MySQL` 可以表示查询步骤，但 Bloom Filter 和 MySQL 不属于缓存层。

本地命中省掉的是后端访问 Redis 和解析缓存 JSON 的工作；返回 HTTP 响应给浏览器仍然需要数据转换。

## 三、为什么选择本地缓存加 Redis

只用 Redis，实现简单、便于共享，但热点每次仍然需要访问 Redis。

只放 Java 内存，读取方便，但每个实例各有一份，内存容量有限，更新也不会自动同步。

因此，我用 Caffeine 保存近期访问的信息，Redis 保存共享缓存，MySQL 作为数据源。Caffeine 负责减少重复 Redis 查询，Redis 负责减少直接查库，两者配合。

选择 Caffeine，是因为它支持容量限制、过期与并发访问，不用自己维护一个不断增长的 Map。容量不足时会结合访问频率和近期性进行取舍，但这不意味着“热门数据永不淘汰”。

## 四、一次正常查询怎么走

```text
收到基础信息查询
    ↓
读取 Caffeine
    ├─ 有仍可使用的数据 → 返回
    └─ 没有 → 检查 Redis 是否已熔断
                  ├─ 不允许访问 Redis → 有限制地查询 MySQL
                  └─ 允许 → 检查 Bloom 及共享新增 ID 记录
                                 ├─ 可以确认不存在 → 返回不存在
                                 └─ 可能存在 → 读取 Redis
                                                ├─ 未过软期限 → 返回并存入 Caffeine
                                                ├─ 软过期、未硬过期 → 返回旧值，尝试后台刷新
                                                └─ 无可用缓存 → 竞争锁，查库并回填
```

“回填”就是把查到的数据重新存进缓存，供后面的请求使用。

当前 Caffeine 最多保存 10,000 条，配置写入后 2 秒过期。业务代码另外检查有效时间：正常最多约 1 秒，不能超过原数据硬期限；软过期旧值复制到本地时最多约 100ms。不能把“配置 2 秒”直接当成每条数据都能用满 2 秒。

## 五、为什么需要 Bloom，还要保留空值缓存

如果一直查询同一个无效 ID，可以短暂缓存“查不到”。但如果请求不停更换 ID，空值缓存每次都还没见过它，就可能不断查询数据库。这叫缓存穿透。

Bloom 在这里先做过滤：判断可能存在就继续；本地判断不存在后，还要核对 Redis 的共享新增 ID 集合。

为什么不能本地一判不存在就拒绝？因为另一台后端可能刚新增了正常数据，本地快照还没更新。新增入口先在共享集合登记；快照和共享集合通过 epoch 对应，状态不可靠时放行到后续受保护查询，不能把索引故障误当成“数据不存在”。

当前按 100 万条、目标误判率 1% 配置，约 958 万位、7 次哈希探测，位数组理论大小约 1.14 MiB，不含其他对象。过滤器启动时构建，每天凌晨 3 点重建；超过设计容量会停用快照过滤。

误判仍可能让无效 ID 查到数据库，查不到后缓存约 1 秒空值。共享新增集合当前不清空，会随新增数量增长；重建与新增通过数据库索引保护行协调，可能阻塞新增。外部绕过登记直接插表，不在这套保证范围内。

## 六、过期时为什么同时用逻辑过期和互斥锁

假设缓存 12:00:00 写入，软期限按 5 秒、硬期限按 15 秒举例：

| 时间 | 处理 |
| --- | --- |
| 12:00:03 | 数据新鲜，直接返回 |
| 12:00:08 | 应该刷新，但还能短暂使用；返回旧值，竞争锁提交后台刷新 |
| 12:00:16 | 旧值不能用了；竞争锁查询数据库，没拿到锁则短暂等缓存 |

实际硬期限是默认 15 秒加不足约 10% 的随机量，并设置 Redis 物理 TTL。

逻辑过期决定“还能不能用旧值”；锁决定“谁负责重建”。锁按 ID 设置，默认租期 5 秒，带本次所有者标识。通过 Lua 核对所有者后才能写缓存、删除锁，避免慢任务失去锁后覆盖新结果或误删新锁。

锁租期到期仍可能产生重复数据库读取，所以不能说任何情况下都只有一个线程查库。无缓存时，抢不到锁的请求按约 10ms 间隔短暂等待，循环预算约 150ms；数据库和网络调用本身也耗时，这不是整个 HTTP 请求的严格 150ms 上限。

后台刷新使用 2 个线程、长度 16 的队列，满了拒绝刷新，不无限堆积任务。这样在新鲜度、请求等待和数据库压力之间取舍。

## 七、Redis 故障时为什么不全部转去 MySQL

如果原本每秒大量请求由 Redis 承接，故障后全部查数据库，可能把数据库也压垮。

我的处理是：能用的本地数据继续用；无法使用时，仅允许一部分请求查库。超限返回 503，让用户稍后重试。

| 机制 | 当前实现 |
| --- | --- |
| 熔断 | 连续 5 次缓存 Redis 读取失败，或读样本的失败、慢调用比例超阈值 |
| 本地数据 | 熔断期间可额外容忍最多约 1 秒，仍不能超过原硬期限 |
| 降级查库频率 | 每实例每个固定秒桶最多 20 次，不是任意滚动一秒的严格上限 |
| 查库并发 | 该缓存组件最多 4 个数据库读取并发，正常重建也受限制 |
| 恢复 | 每秒健康探测，连续 5 次健康后约 10% 试探，保持健康约 10 秒后恢复 |

慢调用监测针对缓存 Redis 读取，不是 HTTP P99，也不代表监测了全部 Redis 命令。降级查询结果当前不重新放入本地缓存。

20 次和 4 并发是单实例限制；多个实例的压力会叠加。没有实现恢复后全量预热。

## 八、管理员改了介绍，其他实例怎么知道

只删 Redis 不够，因为其他后端的 Caffeine 仍可能有旧值。

```text
MySQL 事务内：更新基础信息 + 保存失效任务
    ↓
后台删除 Redis 缓存及相关重建锁
    ↓
通过 Redis Pub/Sub 通知其他实例清理 Caffeine
    ↓
成功后删除对应代次的失效任务；失败保留重试
```

本地回填还会检查失效代次。可以理解为“查询开始时记住版本，写回本地前看有没有收到新的失效通知”，避免旧查询把刚删除的旧值重新放回 Caffeine。

Pub/Sub 不保证通知不丢，短有效期作为兜底，订阅和退订回调会清理本地缓存。这是限制旧数据窗口的方案，不是强一致缓存，也不能保证每个正在执行的请求都立刻看到最新值。

## 九、性能结果到底怎么讲

截图数字没有在当前压测记录中找到对应证据。可以核验的是 [四轮补充实验](../verification/2026-10-05-cache-matrix/README.md)：

| 条件或指标 | 内容 |
| --- | --- |
| 环境 | 同机压测，两个各 384 MiB 的 JVM，本机中间件 |
| 负载 | 正常 Cookie 登录，总并发 32，20 个基础信息对象均匀查询 |
| 运行 | 四轮 A/B，每模式预热 5 秒、测量 20 秒，逐轮交换顺序 |
| P95 中位数 | Redis TTL 12.852ms → 多级缓存 10.856ms，降低约 15.5% |
| 成功吞吐中位数 | 4,605 → 5,812 req/s，提高约 26.2% |
| 错误 | 该组基线 2 次失败，多级缓存 0 次；失败未算入成功样本 |
| 商家回源读取次数 | 基线合计 130 次，多级缓存 320 次 |

中位数是四轮指标中间两值的平均，不是把所有请求合并后重算 P95。目标是 `/v2/shops/{id}` 基础信息接口；真实详情 `/v2/catalog/shops/{id}` 还读取票档、库存和其他展示数据。不能把数字称为整站吞吐或下单 TPS。

为什么多级缓存数据库读取反而更多？因为软过期约 5 秒就刷新，而 TTL 基线约 15 秒过期，刷新策略不同。本地缓存主要减少 Redis 请求，不能据此推断 MySQL 读取必然下降。其他负载组也有波动，不能承诺固定提升。

## 十、面试时可以直接这样讲

校园热门活动开票前后，学生会反复查看同一场活动的介绍。这类信息允许短时间陈旧，因此我在 Redis 前增加了 Caffeine，缓存近期访问的 Java 对象，减少重复的网络请求和 JSON 解析。

对于不断变化的无效 ID，我使用 Bloom Filter 辅助过滤，同时核对共享新增 ID 记录，避免误拦其他实例刚创建的数据。误判通过后查不到，仍会做短期空值缓存。

热点过期时，我区分软期限和硬期限：软过期先返回旧值，通过带所有者校验的 Redis 锁协调后台刷新；硬过期就不再用旧值，没拿到锁只短暂等待。Redis 故障时优先使用仍有效的本地数据，再限制直接查数据库的速率与并发。

更新时在数据库事务里记录失效任务，后台删除 Redis 并通知各实例清本地缓存，通知不可靠的部分用短有效期兜底。这套缓存只服务基础信息，抢票库存和资格由独立交易链路判断。

## 十一、常见追问

**为什么不把 TTL 设长一点？** 命中更容易，但旧值窗口也更长。当前用短本地有效期、软硬期限、主动失效做取舍。

**为什么不直接使用本地 Map？** 还需要自己实现容量淘汰、有效期和并发管理；Caffeine 提供这些能力，但不会自动解决多实例一致性。

**为什么不用旧缓存一直兜底？** 业务只允许短时陈旧，过了硬期限必须停止使用，不能为了可用性无限延长。

**分布式锁是不是绝对只查一次库？** 不是。失效和租约到期都可能出现重叠读取，所有者校验重点是拒绝失效持有者写回。

**怎么验证？** 现有测试覆盖本地命中、失效期间拒绝旧回填、硬期限不被延长、Bloom 故障放行、熔断恢复和限量查库。本次整理只核对源码及历史记录，未重跑测试或压测。
