# 03—Outbox、Kafka 与异步建单可靠性

2026-10-29 更新：消息链路已改为 RocketMQ 异步建单与延迟关单。下文 Kafka、Redis 关单 ZSet 的说明属于此前实现；数据库结构、库存与支付并发设计仍可参考，消息部分以[RocketMQ 改造说明](../engineering/RocketMQ迁移与验收.md)为准。

> 本文保留旧本地交易模式的流程。CORE32主交易将请求、Outbox和权威订单迁到同用户分片，Kafka事件携带user_id；源库存以持久占用另行提交。现行流程与故障窗口见[核心分片学习稿第六部分](../learning/09-核心业务分库分表-按参考文档学习.md)。

## 对应的简历亮点

基于 Kafka 异步建单，通过发送重试与消费幂等保障消息可靠处理，保障已受理请求可恢复、订单不重复。

准确展开时要讲出 Outbox：当前是 **MySQL 请求与 Outbox 同事务 + Kafka 发送重试 + 消费端业务幂等**。异步把建单移到后台，并不自动证明吞吐提升了多少；缓存压测不能作为建单 TPS 证据。

本文围绕一个问题：**学生已经看到“处理中”之后，后台突然退出或消息重复到达，怎么让这次申请有可查询的结果，而不是重复建单或无人处理？**

## 一、先认识参与者，不把几个“成功”混在一起

| 名词 | 在这个项目里指什么 |
| --- | --- |
| 前端请求标识 | 前端为一次抢票操作生成的标识；网络重试复用它，对应 `request_key` |
| 请求记录 ID | 后端生成的 `ux_request.id`，追踪这次申请并查询结果 |
| Outbox | MySQL 的 `ux_outbox` 表，一行表示一条待发送建单事件 |
| 生产者 | 后台读取 Outbox、向 Kafka 发送消息的程序 |
| Kafka | 保存和传递建单事件的消息系统 |
| 消费者 | 后台接收 Kafka 事件，执行 MySQL 建单的程序 |
| 确认消息 | 数据库处理提交后，提交 Kafka 消费进度 |

同一个后端应用里可以同时包含生产者、消费者和定时任务。“多实例”则是同一后端程序运行多份，例如 A、B 两份共同连接 MySQL、Redis、Kafka。

| 状态 | 说明 |
| --- | --- |
| Redis 预占成功 | 暂时拿到名额，不代表订单存在 |
| 请求 ACCEPTED | 请求和发送任务已保存，等待后台处理 |
| 请求 SUCCEEDED | 已创建数据库订单，订单最初仍待支付 |
| 请求 REJECTED / EXPIRED | 本次申请已结束，不再创建订单 |
| 订单 CONFIRMED | 订单已完成；在模拟支付流程中表示支付确认成功 |

接口返回 202 表示“已受理”，前端继续查询结果，不应直接展示支付成功。

## 二、为什么不在接口里直接创建订单

全部同步处理时，用户请求要等待库存扣减、订单及关联记录创建完成，抢票高峰中的数据库压力会直接体现在接口等待上。

异步方案先保存受理记录，把完整建单交给后台，缩短入口需要等待的业务步骤，并通过积压检查限制继续受理。

代价是请求与结果分开，前端需要查询；后台会有积压、重复消息和故障恢复问题。当前受理仍写 MySQL，还要获取活动行锁，并不是“只查 Redis，接口完全不访问数据库”。消息队列也不能无限提高数据库处理能力。

## 三、主流程：这次申请如何走到订单

```text
张三提交票档 101，携带 client-key-001
    ↓
Redis Lua 资格校验和预占
    ↓
入口限流、积压检查
    ↓
MySQL 事务：请求 req-001 ACCEPTED + Outbox event-001
    ↓
事务提交，向前端返回“已受理”
    ↓
后台领取 event-001，组装消息发给 Kafka
    ↓
Kafka 消费者校验事件与数据库记录
    ↓
MySQL 事务：判断请求状态、条件扣库存、建单、写结果和后续任务
    ↓
事务提交后，确认 Kafka 消息处理完成
    ↓
前端查到 SUCCEEDED 和待支付订单
```

Redis 库存确认由独立的持久化动作继续执行，不要求消费者一直等待 Redis 恢复。预占后请求尚未保存的故障窗口，由[库存一致性章节](02-库存一致性-面试学习稿.md)中的核对机制处理，不是 Outbox 直接解决的。

## 四、为什么先写 Outbox，而不是直接发 Kafka

如果“保存请求”与“发送 Kafka”只是两句独立代码，就会出现：

```text
请求已保存 → 发送前程序崩溃 → 数据库有申请，但没有建单消息
```

先发消息也有问题：消费者可能处理到尚未提交的申请，或者数据库事务随后回滚。`try/catch` 无法捕捉进程突然退出，更无法在重启后凭空记起待发送任务。

因此，在同一个 MySQL 事务内保存：

```text
ux_request：这次申请已受理
ux_outbox：这次申请需要发送建单事件
```

一起提交或一起回滚。Outbox 把发送意图留在数据库，后台发送失败保留记录、稍后重试，应用重启也能继续找。

它保证的是“已持久受理的请求有发送记录”，不让 Redis 和 MySQL 自动变成一个事务，也不能让 Kafka 与 MySQL 发送标记原子提交。

## 五、Outbox 到底长什么样，怎么变化

假设 12:00:00 受理了张三的申请。ID 为便于阅读的缩写，时间是示例，不是实测记录。

| 字段 | 初始值 | 含义 |
| --- | --- | --- |
| id | event-001 | 事件 ID |
| request_id | req-001 | 对应的后端请求记录 ID |
| activity_id | 101 | 票档 ID |
| created_at | 12:00:00 | 创建时间 |
| next_at | 12:00:00 | 允许下次尝试发送的时间 |
| attempts | 0 | 被后台领取的次数，通常对应发送尝试 |
| owner | NULL | 本次领取标识，初始无人领取 |
| lease_until | NULL | 本次领取有效到什么时候 |
| sent_at | NULL | 是否已记录发送成功；有值时是具体时间 |

当前表不保存完整消息正文，后台根据字段组装：

```json
{
  "schemaVersion": 1,
  "eventId": "event-001",
  "requestId": "req-001",
  "activityId": 101
}
```

Kafka 消息 key 使用票档 ID。用户和价格不能随消息随意指定，建单根据已持久化请求和服务端票档数据判断。

同一行记录的正常变化：

| 阶段 | attempts | owner | lease_until | sent_at |
| --- | ---: | --- | --- | --- |
| 创建 | 0 | NULL | NULL | NULL |
| 12:00:01 领取 | 1 | owner-001 | 12:00:16 | NULL |
| 发送成功 | 1 | NULL | NULL | 12:00:01.100 |
| 建单、支付或关闭订单后 | 保持 | 保持 | 保持 | 保持发送时间 |

失败时 `sent_at` 仍为 NULL，清空领取信息，把 `next_at` 推迟；到时间后重新领取。领取时先增加 attempts，因此它不严格等于已经发出的网络请求数量。

**`sent_at = NULL` 不等于 Kafka 一定没收到；`sent_at` 有值也不代表订单成功。**正常发送成功后不立即删除 Outbox，因为消费端还要校验事件对应关系。

## 六、多实例怎样领取，为什么仍可能重复发送

领取时用短事务执行 `FOR UPDATE SKIP LOCKED`：锁住准备领取的行，其他实例暂时跳过这行，登记本次 owner、15 秒租约和次数，然后提交释放行锁。

“租约”可以理解成领取期限。行锁保护领取登记的短过程，租约保护之后那段发送时间；不是把数据库锁一直持有到网络发送完成。

领取者退出且租约过期后，其他实例可以接手。更新发送成功结果时也会检查 owner，不能随意覆盖别人的领取结果。

但下面的重复仍然不可避免地需要处理：

```text
A 发送成功，Kafka 已收到
    ↓
A 更新 sent_at 前退出
    ↓
数据库仍显示未完成
    ↓
租约到期，B 接手并重发同一事件
```

租约到期时，原发送者也可能只是慢，并非真正退出，因此租约不能当成“绝对不会重复”的保证。

## 七、Kafka 配置保护了什么，没保护什么

当前配置 `acks=all`、生产者幂等，后台等待发送结果成功后才标记 Outbox；发送失败按退避时间重试。

`acks=all` 的效果还取决于同步副本和副本配置，本地单节点不能描述成已经具有多副本容灾能力。

生产者幂等主要处理生产者协议层发送重试，不能把“应用重新读取 Outbox 后重新发的同一业务事件”一律去掉，也不能替 MySQL 保证只建一单。

Kafka 的事务能力不会自动把 MySQL 扣库存和订单提交纳入 Kafka 事务。当前明确采用业务幂等处理重复，而不是宣称消息只投递或代码只执行一次。

## 八、重复消费时，为什么不会重复扣库存和建单

可能的场景是：MySQL 已保存订单，但消费者提交 Kafka 消费进度前退出，恢复后又读到同一条消息。

当前三层保护配合：

1. **状态判断。**锁定并读取请求，只有 ACCEPTED 才进入建单；已成功、拒绝或过期则返回已有结果。
2. **同一事务。**条件扣库存、建订单、更新请求状态、记录后续动作一起提交或回滚。
3. **唯一约束。**用户与请求标识、订单中的请求 ID、票档与用户组合分别唯一。

例如第一次处理后 `req-001` 已是 SUCCEEDED，第二次收到 event-001，就直接返回已有结果。这里还保留活动行锁和请求行锁，不能把它简化成“先查一个状态然后无锁地更新”。

JVM 内存 Set 记录已处理消息不够：重启会丢、多实例不共享，而且内存记录与建单不能同一个数据库事务提交。

## 九、为什么先提交数据库，再确认消息

```text
数据库事务提交成功
    ↓
确认 Kafka 消费进度
```

| 失败位置 | 后果和处理 |
| --- | --- |
| 数据库提交前失败 | 事务回滚，不确认消息，后续重试 |
| 数据库提交后、确认前退出 | 可能再次消费，状态判断阻止重复业务效果 |
| 先确认再建单时退出 | 可能消费进度已前进，但订单没保存，所以当前不这样做 |

当前 `enable-auto-commit=false`，监听器使用手动即时确认。Redis 后续动作已经持久化，即使它暂时更新失败，也不阻塞数据库已完成后的消费确认。

## 十、坏消息和数据库故障怎么区分

消息格式不合法、版本不支持、Kafka key 与票档不匹配、无法对应持久化事件等，不能一直当成正常抢票重试。消费者先把原始位置、消息内容和原因写入 `ux_poison` 隔离表，保存成功后才确认；隔离保存失败则不确认。

数据库临时不可用等基础设施异常则抛出，当前错误处理器按约 1 秒间隔无限重试，不配置“固定次数后自动跳过”。这避免故障时悄悄丢弃，但也可能拖慢所在分区，需要观察积压并修复依赖。

管理员可以针对已有 Outbox 事件执行受保护的重发操作，重发后仍受业务状态约束。当前没有实现“固定次数重试 → 死信主题 → 自动补偿”的流程，也没有 RabbitMQ confirm、return 机制。

## 十一、入口保护和观察指标

当前 Redis 固定窗口限制同一用户同一票档约每秒 5 次、单票档约每秒 200 次；每实例信号量限制同时受理 16 个请求。完成受理就释放名额，不等待整笔订单支付。

入口还查询数据库里 ACCEPTED 请求的数量和最早创建时间，默认达到 5,000 条或等待至少 60 秒时暂停新受理。这是受理检查阈值，不是 Kafka backlog 的直接读取，也不是并发下待处理总量的绝对硬上限。

主要看 Outbox 未发送数量及最老年龄、请求等待、消费异常隔离、Redis 动作积压和库存不变量。队列不是无限缓存池，不能只看入口接得快。

## 十二、面试时可以直接这样讲

我把抢票拆成受理和异步建单。Redis 预占通过后，先在同一个 MySQL 事务中保存 ACCEPTED 请求和 Outbox 事件，再返回处理中，前端查询最终结果。

后台读取 Outbox 发送 Kafka，发送成功才标记，失败保留任务重试。多实例通过数据库行锁和租约领取，退出后可以接手，但发送成功与数据库标记之间仍有窗口，可能重发。

所以消费端按事件与请求的对应关系校验，只有 ACCEPTED 才建单。库存扣减、订单创建、请求结果和后续动作一起提交，数据库唯一约束再兜底。提交后才确认 Kafka 进度，允许消息重复到达，但不重复扣库存、建订单。

数据库暂时故障不直接确认跳过，格式异常则先持久化隔离。已经保存的请求超过处理期限也可以结束为过期，迟到消息不能重新建单。这样恢复目标是让申请有明确结果，而不是保证每次受理都一定成功出票。

## 十三、追问与验证

**Outbox 能保证消息立即送达吗？** 不能，只保留可重试发送意图，依赖恢复、后台运行和无永久错误；还需监控积压。

**请求已经过期，Outbox 后来才发出去怎么办？** 消费端看到终态就返回，不重新扣库存建单。

**提高并发性能体现在哪里？** 入口不用等待完整建单，且能缓冲短时波动；实际端到端容量取决于数据库、锁和消费能力。当前不能拿基础信息查询的 QPS 证明下单提升。

**已有验证是什么？** 测试覆盖重复消费、迟到消息不能复活过期请求、数据库失败不确认、隔离保存失败不确认、发送窗口有界和已完成建单不等待 Redis 修复。本文核对代码和已有记录，未重跑测试。
