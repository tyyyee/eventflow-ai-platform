# 04—延迟关单、支付并发与退款补偿

2026-10-29 更新：消息链路已改为 RocketMQ 异步建单与延迟关单。下文 Kafka、Redis 关单 ZSet 的说明属于此前实现；数据库结构、库存与支付并发设计仍可参考，消息部分以[RocketMQ 改造说明](../engineering/RocketMQ迁移与验收.md)为准。

> 本文保留旧本地交易模式。CORE32模式的订单、支付与关单任务在用户分片内协调，库存回补及模拟渠道退款通过跨库幂等任务完成；现行流程见[核心分片学习稿第六部分](../learning/09-核心业务分库分表-按参考文档学习.md)。

这部分围绕一个具体问题展开：**学生抢到票后一直没付款，怎么释放名额；付款和关单同时发生时，怎么保证订单、库存和付款结果正确。**

本文按当前代码整理。支付使用模拟渠道，不涉及真实扣款；面试时需要明确这个范围。

## 简历上的亮点

**延迟关单与并发控制：**基于 Redis ZSet 和持久化任务实现延迟关单，通过 CAS 条件更新处理支付与关单并发，避免订单状态覆盖及库存重复回补；支持遗漏任务补偿和关单后付款的退款处理。

当前实现还使用活动行锁协调并发，不能描述成只靠 CAS 完成全部并发控制。

## 先认识几个词

| 名词 | 通俗解释 |
| --- | --- |
| 延迟关单 | 订单创建后先给用户付款时间，到期仍未完成就关闭 |
| ZSet | 成员带分数的有序集合，这里按支付截止时间排列待处理任务 |
| 持久化任务 | 保存在 MySQL 的处理记录，应用退出后仍能继续读取 |
| CAS 条件更新 | 当前状态仍符合预期才修改，通过影响行数判断成功与否 |
| 库存回补 | 将已释放的票额重新计入可用库存 |
| 退款任务 | 记录这笔付款还需要退回，不表示已经完成退款 |

异步建单解决“申请怎样创建订单”，本篇解决“订单创建后怎样完成或结束”。Outbox 的发送时间不负责记录订单是否付款或关闭。

## 一、背景：抢到名额后，为什么还要延迟关单

是这样的，我先说一下业务背景。

学生抢票后，系统会创建一笔待支付订单，同时占用一张票。如果学生一直不付款，这张票就会一直被占着，其他学生也买不到。

因此，我给订单设置了 **5 分钟支付期限**。超过期限还没有完成支付，就关闭订单，把名额释放出来。

但实现时，不能只写一个“5 分钟后取消订单”的定时任务，还需要解决三个问题：

1. 应用退出、Redis 故障后，到期订单还能继续处理。
2. 支付和关单同时发生时，不能互相覆盖订单状态，也不能重复释放库存。
3. 订单已经关闭后才收到付款通知，需要记录付款并退款。

## 二、先明确：订单有哪些状态

这里讨论的是**订单状态**，与异步抢票章节中的请求状态不同。

| 订单状态 | 含义 |
| --- | --- |
| `PENDING_CONFIRM` | 待支付、待完成 |
| `CONFIRMED` | 订单已完成；在模拟支付流程中表示付款确认成功 |
| `CANCELLED` | 待支付订单被用户取消 |
| `EXPIRED` | 订单超过支付期限而关闭 |

主要状态变化是：

```text
PENDING_CONFIRM
    ├─ 截止时间前完成支付 → CONFIRMED
    ├─ 用户取消 → CANCELLED
    └─ 超过支付期限 → EXPIRED
```

当前不会把已经完成的订单直接改成取消或过期，也不会因为收到迟到付款，就把关闭的订单重新改为完成。

另外，请求记录变成 `SUCCEEDED`，表示建单成功；之后订单取消或过期，请求记录仍然可以保持 `SUCCEEDED`。

## 三、整体流程怎么走

```text
创建待支付订单
    ↓
在同一个 MySQL 事务中：
保存订单 + 保存到期关单任务
    ↓
后台把关单任务加入 Redis ZSet
以支付截止时间作为分数
    ↓
定时查询已经到期的任务
    ↓
进入数据库事务：
检查订单状态和截止时间
    ↓
通过条件更新，把待支付订单改为已过期
    ↓
只有首次关闭成功，才回补 MySQL 库存
并记录需要恢复 Redis 库存的任务
    ↓
事务提交成功
    ↓
清理 ZSet 中的任务
后台继续执行 Redis 库存恢复
```

与此同时，还有一个兜底任务：

```text
定时查询 MySQL 中：
已经到期、尚未完成的关单任务
    ↓
执行同一套关单逻辑
```

这样，即使 Redis 中的任务没有成功写入，或者 ZSet 丢失，数据库里仍然有记录可以继续处理。

## 四、为什么同时使用 Redis ZSet 和数据库任务表

### 先考虑过哪些方案

| 方案 | 可以解决什么 | 当前没有单独采用它的原因 |
| --- | --- | --- |
| Java 内存定时器 | 进程运行时可以安排延迟任务 | 重启会丢调度记录，多实例接手还要另外设计 |
| 只查数据库到期任务 | 可以持久恢复，当前也作为兜底 | 高频检查会持续给 MySQL 增加查询，需结合索引和任务量评估 |
| 只用 Redis ZSet | 容易按截止时间找出到期的一批任务 | 不能单独覆盖数据库提交后尚未投递、Redis 故障或数据丢失 |
| ZSet 加数据库任务表 | Redis 维护到期提醒，MySQL 留下可恢复记录 | 多一套任务投递和核对逻辑，需要接受短暂重复执行 |

这不是说数据库扫描一定慢，也不是说其他延迟方案不能使用；当前根据已有 Redis 和较短支付期限，选择了这套可以核对、可恢复的实现。

### 1. ZSet 方便按到期时间找任务

ZSet 是 Redis 的有序集合，每个成员都可以带一个分数，Redis 按分数排序。

在这个项目中：

- 成员保存抢票请求 ID，通过它定位订单。
- 分数保存支付截止时间的毫秒时间戳。

例如：

```text
请求 A → 12:05 到期
请求 B → 12:06 到期
请求 C → 12:10 到期
```

到了 12:06，后台就查询“分数小于等于当前时间”的成员，找到 A、B，检查它们是否需要关闭。

**不是让 Redis 自动执行关单，而是 Java 后台定时从 ZSet 查出到期任务，再执行数据库操作。**

当前定时任务的执行间隔为 1 秒，每次最多取 100 条，因此不承诺恰好在截止时间那一毫秒完成关单。

当前关单队列默认 key 是 `ux:close:due`，成员是请求记录 ID，分数是截止时间的毫秒时间戳。例如：

| member | score 的含义 |
| --- | --- |
| req-001 | 订单 A 的支付截止时间 |
| req-002 | 订单 B 的支付截止时间 |

同一个 member 重复加入不会产生多个相同成员，只会更新分数，但多个实例仍可能同时读到并处理它，所以数据库处理必须支持重复。

“查询到期成员”只是读取，不提前从 ZSet 弹出；关单处理完成后才删除。这里没有依赖 Redis key 过期通知，也不是向 Kafka 发送一条原生延迟消息。

和库存预占检查的区别是：

| ZSet | 检查什么 | 到时间后做什么 |
| --- | --- | --- |
| `ux:reserve:{票档ID}:pending` | 预占后有没有受理、建单结果 | 核对数据库，再决定确认、等待或释放 |
| `ux:close:due` | 已有订单有没有超过支付期限 | 检查订单，必要时关闭并释放票额 |

### 2. 数据库任务表负责保存不能丢的处理记录

如果只把任务放进 Redis，会有一个失败窗口：

```text
MySQL 订单创建成功
    ↓
还没写入 Redis，应用退出
    ↓
订单存在，但没有对应的延迟提醒
```

因此，我把订单和 `ux_close_task` 关单任务放在同一个 MySQL 事务里保存：

```text
一起保存成功
或者
一起回滚
```

后台再读取任务表，把任务加入 ZSet。

任务表关键字段如下：

| 字段 | 含义 |
| --- | --- |
| request_id | 对应哪个抢票请求和订单，也是任务主键 |
| user_id | 订单所属用户 |
| due_at | 支付截止时间 |
| next_enqueue_at | 下次允许投递进 ZSet 的时间 |
| done_at | 任务完成时间，NULL 表示尚未完成 |

订单完成支付或被取消后，任务也可以标记完成。`done_at` 有值表示这件到期检查工作已结束，不等于一定发生了超时关闭。

可以把两者的分工理解为：

> Redis 保存按时间排序的提醒，MySQL 保存这件事还需要处理的记录。

## 五、任务漏执行或者服务退出，怎么恢复

我主要处理下面几个失败窗口。

| 出问题的位置 | 当前处理方式 |
| --- | --- |
| 建单事务没有提交成功 | 订单和关单任务一起回滚 |
| 数据库已提交，还没加入 ZSet | 后台从数据库任务表继续投递 |
| 已从 ZSet 读到任务，关单前应用退出 | 查询时没有提前删除任务，下次仍能读到 |
| 关单已成功，还没删除 ZSet 成员 | 再次执行时发现订单已经结束，不重复回补 |
| Redis 不可用或 ZSet 丢失 | 直接查询数据库中的到期任务并处理 |

当前代码还有两个具体设置：

- 未完成的任务允许每隔约 **30 秒**重新加入 ZSet。
- 兜底任务每隔 **10 秒**查询数据库中的到期未完成任务，每批最多 100 条。

这些是调度间隔，不是故障后一定能在对应秒数内处理完成的承诺；任务积压和数据库故障仍然会造成延迟。

这里的“遗漏任务补偿”，主要指**任务已经存在于数据库，但没有进入 ZSet，或者没有被成功执行**。不是在没有任何记录的情况下，凭空找回任务。

## 六、支付与关单同时发生，怎么避免状态被覆盖

假设一笔订单接近截止时间：

```text
支付处理：准备把订单改成 CONFIRMED
关单任务：准备把订单改成 EXPIRED
```

如果只先查询状态，再执行不带条件的更新，迟到的操作就可能覆盖已经写入的结果。

因此，我使用带旧状态条件的更新：

```sql
UPDATE ux_order
SET state = ?
WHERE id = ?
  AND state = 'PENDING_CONFIRM';
```

意思是：

> 只有订单现在仍是待支付，才允许修改。

这就是这里所说的 **CAS 条件更新**：先比较当前状态是否符合预期，符合才修改。

根据 SQL 影响行数判断：

- 影响 **1 行**：本次成功改变了订单状态。
- 影响 **0 行**：当前状态已不符合条件，不能继续按“修改成功”处理。

当前实现还会在事务中锁定对应的活动行，协调支付、取消、关单和库存恢复。

所以准确说法是：

> 通过活动行锁协调并发，再通过 CAS 条件更新防止订单状态被重复修改。

不能说完全没有锁，也不能把它描述成只靠 CAS 就处理了全部并发问题。

## 七、是不是谁先抢到锁，谁就一定成功

**还要检查支付截止时间。**

当前使用数据库时间判断订单是否到期，主要分三种情况。

### 情况一：未到截止时间，支付确认先成功

```text
PENDING_CONFIRM → CONFIRMED
```

后续关单任务读取到已完成状态，就不再关闭，也不回补库存。

### 情况二：订单到期，关单先执行成功

```text
PENDING_CONFIRM → EXPIRED
```

此时释放库存。之后即使收到付款通知，也不会重新打开订单，而是记录退款任务。

### 情况三：已经过期，但关单任务还没执行，付款通知先到

数据库里可能还显示 `PENDING_CONFIRM`，但支付处理仍然会检查截止时间。

如果已经到期，就关闭订单、释放库存，并把这笔付款记入退款流程。

因此：

> 关单任务晚执行，不代表用户获得了额外支付时间。

当前判断依据是后端处理时的数据库时间，没有实现按真实支付渠道的付款时间裁决迟到通知。

## 八、怎么保证库存只回补一次

库存不能因为每次收到关单任务就加一，否则任务重复执行几次，票数就会凭空增加。

我的处理方式是：**只有本次成功把待支付订单改成取消或过期，才执行库存回补。**

简化后的逻辑是：

```text
执行订单状态条件更新
    ↓
影响行数是否为 1？
    ├─ 是 → MySQL 库存加 1，记录 Redis 库存恢复任务
    └─ 否 → 不回补库存
```

以下操作放在同一个数据库事务里：

```text
订单改为关闭
MySQL 库存加 1
保存 Redis 库存恢复任务
标记关单任务完成
```

中间任何一步失败，整笔事务回滚，避免出现“订单关闭了，库存却没有恢复”的数据库内部不一致。

Redis 的库存恢复由后台另外执行。它不属于 MySQL 事务，但恢复任务已经持久化，执行失败可以重试。

Redis Lua 还会检查这次预占的状态：

- 尚未恢复：增加库存并标记已恢复。
- 已经恢复：不再增加库存。

因此，MySQL 和 Redis 分别通过状态判断，避免重复回补。

当前规则下，订单取消或超时后虽然释放票额，**用户原有的购买限制仍然保留**，不会因此获得重新购买同一票档的资格。

## 九、订单关了，为什么还要处理付款和退款

因为“订单关闭”和“付款通知到达”可能存在时间差。

例如：

```text
用户之前已创建支付单
    ↓
订单到期，被系统关闭，名额已释放
    ↓
随后收到该支付单的付款通知
```

这时不能直接忽略通知，因为付款需要有明确记录；也不能直接恢复订单，因为名额可能已经分配给其他学生。

当前处理是：

```text
收到付款通知
    ↓
检查用户归属、金额和渠道流水号
    ↓
发现订单已经关闭
    ↓
在同一个数据库事务中：
记录付款流水 + 保存退款任务
    ↓
后台执行退款
    ├─ 成功 → 标记退款完成
    └─ 失败 → 保留任务，稍后重试
```

**记录退款任务，不等于退款已经完成。**

当前退款失败后采用退避重试，等待时间逐步增加，单次等待上限为 60 秒。

当前几张记录各自负责不同结果：

| 表 | 正常支付示例 | 关闭后付款示例 |
| --- | --- | --- |
| `ux_order` | CONFIRMED | EXPIRED 或 CANCELLED，不复活 |
| `ux_payment` | PAID | REFUND_PENDING，退款全部完成后 REFUNDED |
| `ux_payment_receipt` | APPLIED | REFUND_PENDING，退款后 REFUNDED |
| `ux_refund` | 不需要这笔退款任务 | 保存退款金额、重试时间和完成时间 |

支付单刚创建时为 OPEN，只代表可以继续进行模拟支付，不代表已付款。付款金额从订单中读取，通知时核对金额及用户归属，不由前端随意指定结果。

为了避免重复退款：

- 同一渠道流水重复通知，返回已有处理结果。
- 退款任务按渠道流水唯一记录。
- 模拟退款渠道也按同一流水去重。

例如，模拟渠道已经退款成功，但程序在更新本地结果前退出，恢复后仍用原流水重试，不会再次产生退款效果。

另外，如果订单已经正常付款完成，随后收到另一笔不同流水的重复付款，当前会对额外那笔付款创建退款任务，原订单保持完成状态。

这里的退款处理针对**迟到付款和额外重复付款**，不代表已经实现已支付订单的通用退票业务。

## 十、怎么证明这些逻辑不是只停留在设计上

现有测试代码覆盖了：

- 订单和关单任务一起回滚。
- 重复关单不重复恢复库存。
- Redis 队列丢失后，从数据库任务继续关单。
- 到期付款与关单并发，最终关闭订单、只回补一次。
- 支付与取消并发，最终保留一个正确结果。
- 同一付款通知重复到达，不重复产生业务效果。
- 退款失败后保留任务，重试能够继续执行。
- 模拟渠道退款成功、本地未确认时重试，不产生第二次退款。
- 多笔迟到付款全部退款完成后，才显示整体退款完成。

这些是当前代码中的测试覆盖，本次文档整理没有重新运行测试。

运行时还可以关注两个指标：

- 已经到期、尚未处理完成的关单任务数。
- 尚未完成的退款任务数。

它们持续增长，就说明处理链路可能出现故障或积压。

## 十一、面试时可以直接这样讲

学生抢票后，我会创建一笔待支付订单，给出 5 分钟支付期限。为了避免订单一直占着名额，我实现了延迟关单。

建单时，我把订单和关单任务放在同一个 MySQL 事务中保存。后台再把任务加入 Redis ZSet，以支付截止时间排序，定时查询到期任务。同时，数据库任务表会定期检查到期但没处理完的记录，所以 Redis 故障或者应用重启后，任务仍然可以继续执行。

支付和关单可能同时发生，因此我通过活动行锁协调并发，并且只允许待支付状态通过条件更新转成已完成、已取消或者已过期。只有本次成功关闭订单，才回补数据库库存，并在同一事务记录 Redis 库存恢复任务，防止重复关单导致库存重复增加。

如果付款通知到达时订单已经关闭，我不会重新打开订单，而是记录付款流水和退款任务。退款失败后继续重试，并使用渠道流水做幂等，避免重复退款。

当前支付渠道是模拟实现。我主要验证的是订单状态、库存恢复、任务重试和迟到付款退款这些处理逻辑。

## 十二、常见追问和实现范围

**为什么只查订单状态不够？** 只查到待支付，再不带条件地修改，无法单独防止并发覆盖。当前既有活动行锁协调，也有带旧状态的 UPDATE，并且还要检查截止时间。

**CAS 是不是把所有逻辑都变成无锁？** 不是。它是在数据库执行条件更新；当前还有活动行锁，数据库也会管理写锁，热门票档仍存在竞争。

**支付和关单，谁先到就一定赢吗？** 不是。超过截止时间，即使支付处理先进入，也不能简单确认订单。当前按处理时数据库时间裁决，未实现真实渠道付款时间的核对。

**退款是不是可以把数据库事务回滚一下？** 不是。付款效果和本地状态可能已经发生，不能靠回滚本地事务把钱自动退回，需要独立退款动作。当前用持久化模拟渠道账本验证这个过程。

**退款重试会不会一直失败？** 可能，所以持久化任务只是保留处理依据，不是无条件成功保证。需要观察积压并修复故障。若接真实渠道，还要补齐验签、查单、主动关单、资金对账、退款 API 和渠道幂等约定。

**为什么部分退款完成还显示待退款？** 同一支付单可能对应多笔迟到付款。只有所有待退款流水完成，整体状态才改为 REFUNDED；之后再来一笔迟到付款，会再次进入待退款。

**已支付的正常订单可以主动退票吗？** 当前这段实现不能代表通用退票业务。它主要处理关闭后付款，以及额外重复付款；正常已完成订单不会被待支付取消接口直接改成已取消。
