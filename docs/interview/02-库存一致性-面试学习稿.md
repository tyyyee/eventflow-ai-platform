# 02—库存预占、数据库扣减与故障恢复

> 本文解释旧本地交易模式。CORE32主交易中库存与订单已经跨库，新增持久库存占用与分片动作补偿；当前面试请同时阅读[核心分片学习稿第六部分](../learning/09-核心业务分库分表-按参考文档学习.md)，不要沿用下文“库存与订单同一事务”的范围结论。

## 对应的简历亮点

基于 Redis Lua 实现库存预扣和一人一单校验，MySQL 通过条件扣减和唯一索引防止超卖和重复下单；通过后台预占核对及持久化 Redis 动作，处理请求中断、订单取消、超时和应用重启后的库存恢复。

本文重点回答：**一张票从被预占到建单、取消，中间任何一步失败，怎么保证不多卖、不重复扣，也不一直占着不释放？**

## 一、业务规则和“一人一单”到底指什么

校园热门演出只有有限票额，开抢时会有大量请求。当前交易按票档限制购买：同一用户对同一票档最多有一笔订单，取消或过期后也不能重新购买这个票档。

代码中的 `activity_id` 在交易链路对应限量票档，不应把“一人一单”扩大解释成一个学生整个校园活动平台只能买一张票。

先明确几个词：

| 名词 | 通俗解释 |
| --- | --- |
| Redis 预占 | 先暂时拿走一个可抢名额，还没正式创建订单 |
| MySQL 库存扣减 | 建单时正式减少数据库的可用票额 |
| 请求记录 | 保存某个用户这一次申请的状态，表为 `ux_request` |
| 订单记录 | 建单成功才有，表为 `ux_order`，后续可支付、取消或过期 |
| 幂等 | 同一操作重复执行，不多扣库存、不多建订单、不多还票 |
| 补偿任务 | 根据已确定的结果，把之前未完成的库存处理继续做完 |

## 二、为什么不能只靠 Redis，或者只靠 MySQL

### 1. 只靠数据库

MySQL 条件扣减和唯一约束能保护库存正确性，但大量售罄请求、重复点击也会进入数据库，造成连接和热点行锁压力。

### 2. 只靠 Redis

Redis 处理快速，但 Redis 预扣成功不等于数据库订单已经创建。进程退出、网络异常、Redis 数据丢失，都可能让两边暂时对不上。

### 3. 当前取舍

先用 Redis Lua 做预占和重复资格检查，减少一部分明显无效的数据库写入；建单仍由 MySQL 条件扣减、唯一约束和事务保护；不同步骤之间用持久化状态和后台任务恢复。

**Redis Lua 与 MySQL 不属于同一个事务。**Lua 把 Redis 内的检查和修改作为一个不可被其他命令插入的过程执行，但不能一起回滚 MySQL 操作，也不等于通用事务回滚机制。

正常受理仍然写 MySQL，且当前使用同一票档的活动行锁协调受理、建单和补偿，因此不能说 Redis 预占后完全没有数据库瓶颈。

## 三、正常抢一张票，库存怎么变化

假设票档 101 有 100 张票，张三用户 ID 为 1001。下面 ID 为便于阅读的缩写，真实业务使用 UUID 等标识。

```text
前端提交票档 101，携带本次请求标识 client-key-001
    ↓
Redis Lua 校验同一请求是否重试、用户是否买过、库存是否足够
    ↓
Redis 预扣：100 → 99，记录用户和预占状态
    ↓
入口限流与待处理积压检查
    ↓
MySQL 同一事务：请求 ACCEPTED + Outbox 事件
    ↓
后台发送 Kafka，消费者执行建单事务
    ↓
MySQL 有库存才扣：100 → 99
创建待支付订单，请求改为 SUCCEEDED
同时保存确认 Redis 预占的动作
    ↓
提交后，后台把 Redis 预占标记为已确认
Redis 库存仍是 99，不再扣第二次
```

| 阶段 | Redis 库存 | MySQL 库存 | 请求状态 | 订单 |
| --- | ---: | ---: | --- | --- |
| 初始 | 100 | 100 | 无 | 无 |
| Redis 预占后 | 99 | 100 | 可能尚无 | 无 |
| 正式受理后 | 99 | 100 | ACCEPTED | 无 |
| 建单提交后 | 99 | 99 | SUCCEEDED | PENDING_CONFIRM |
| 截止前支付确认 | 99 | 99 | SUCCEEDED | CONFIRMED |
| 或取消、过期且恢复完成 | 100 | 100 | SUCCEEDED | CANCELLED / EXPIRED |

两套库存不是对同一个数据库字段扣两次，而是分别维护“Redis 可抢名额”和“数据库正式库存”。处理中允许短暂不同，不能要求每一瞬间数字都相等。

## 四、Lua 为什么要把判断和预扣放一起

如果分开发命令：先查库存、再判断没买过、再扣一张，就可能两个请求都读到最后一张票可用，或者同一用户的两个请求都通过资格检查。

当前一个 Lua 脚本中依次完成：

```text
检查恢复版本是否可用
检查“用户 + 本次请求标识”有没有处理记录
检查用户是否已经有占位或购买记录
检查剩余库存
扣减库存
保存用户占位、预占状态和待检查时间
```

Redis 在执行脚本时不会让别的命令插入这段过程，避免“大家都检查通过后再分别扣减”的并发空隙。

同一次操作超时后，前端复用原请求标识。Lua 发现已有预占就返回已有状态，不再减一。如果用户换了请求标识重复买，用户占位检查仍会拦截。

## 五、MySQL 怎么守住正式库存和重复建单

### 1. 有库存才减

```sql
UPDATE ux_activity
SET available = available - 1
WHERE id = ? AND available > 0;
```

影响 1 行才继续建单；影响 0 行，说明没扣到票，将请求拒绝，不创建订单。

### 2. 库存、订单、结果一起提交

建单事务里完成：锁定活动和请求、核对事件、判断请求状态、条件扣库存、创建订单、更新请求结果、写 Redis 后续动作及关单任务。

任何一步失败，整笔数据库事务回滚。订单写入失败，前面的数据库扣减也回滚，不留下“少一张票却没有订单”的半成品。

### 3. 唯一约束保护不同层面的重复

| 约束 | 作用 |
| --- | --- |
| `ux_request(user_id, request_key)` 唯一 | 同一次提交重试时不生成第二次申请 |
| `ux_order(request_id)` 唯一 | 同一个申请最多创建一笔订单 |
| `ux_order(activity_id, user_id)` 唯一 | 同一个用户不能在同一票档重复建单 |

原请求标识不能换票档重复使用，后端还会核对请求内容摘要。请求已不是 `ACCEPTED` 时，消费端直接返回已有结果，避免重复操作。

## 六、Redis 占了票，但请求还没存进 MySQL 就退出了

这个失败窗口没有请求记录，也没有 Outbox，单靠 Kafka 重试找不回来。

所以预占时会把任务放进待检查 ZSet。例如票档 101：

```text
key：ux:reserve:{101}:pending
member：1001:client-key-001
score：预定检查时间的毫秒时间戳
```

当前入口把首次检查时间设为大约 5 秒后。ZSet 用来按时间筛选“已经该检查的预占”，不是到点自动归还库存。它和订单创建后的关单 ZSet 是两份不同用途的记录。

后台检查时，要先去数据库确定结果，不能“查不到就加一”。因为原请求可能只是慢了：如果先还票，旧请求随后提交，就会让已经释放的名额又对应到有效建单申请。

当前受理与补偿裁决使用同一活动行锁：

| 先后顺序 | 处理结果 |
| --- | --- |
| 受理先提交 | 补偿看到已有请求，按数据库状态处理 |
| 补偿先确认没有受理记录 | 先写入该用户、本次标识的 `EXPIRED` 记录及释放任务，再释放预占 |
| 原请求随后迟到 | 读取到已有过期结果，不再重新受理和写建单 Outbox |

如果请求仍是 `ACCEPTED`，后台会把预占检查时间调整到请求处理截止时间，而不是因为最初 5 秒到了就还票。请求截止时间来自活动配置，与订单建成后的 5 分钟支付期限不同。

核心是：**先留下“这次申请已经结束”的数据库记录，再释放名额，防止迟到请求继续建单。**数据库不可用时不能假装已经确认失败，需要保留状态等待恢复。

## 七、数据库已提交，但 Redis 更新失败怎么办

在保存业务结果的同一个 MySQL 事务里，把“Redis 还需要做什么”写入 `ux_reservation_action`。后台执行，失败保留并退避重试；成功再填写 `applied_at`。

| 动作 | 业务含义 | 是否保留购买限制 |
| --- | --- | --- |
| CONFIRM | 建单成功，预占转为已确认，不再扣库存 | 保留 |
| RELEASE | 申请失败或被判定放弃，释放预占 | 仅移除属于本次请求的用户占位 |
| RELEASE_KEEP | 已存在该用户订单，释放多余预占 | 保留 |
| RESTORE | 已建订单取消或过期，归还票额 | 保留 |

不能统一“失败就库存加一、删除用户记录”。例如张三已经有订单，多余预占需要释放，但已购买限制不能删；否则张三又能购买同一票档。

Lua 同时检查预占状态、修改库存和记录新状态。第一次执行恢复后会标记已恢复，同一动作重试不再加库存。`CONFIRM` 动作迟到且状态已恢复时也不会把它重新变成有效占票。

MySQL 侧只有首次成功关闭待支付订单，才加库存并写 RESTORE；这些步骤同事务提交。Redis 更新暂时失败不阻塞已完成建单的 Kafka 确认。

## 八、应用重启和 Redis 数据丢失，是两种恢复

### 应用重启：继续未完成任务

MySQL 的请求、Outbox、Redis 动作和关单任务还在，后台可以继续执行。Redis 预占状态仍在时，也可以继续扫描待检查记录。不是程序重启就把所有库存加回去。

### Redis 交易数据丢失：停止盲目抢票，显式恢复

不能发现 Redis 库存不存在，就直接读取 MySQL 剩余库存重置，因为还可能存在处理中、尚未建单的请求。

当前缺少交易状态时拒绝新预占，要求管理员调用恢复入口：

```http
POST /v2/admin/activities/{id}/recover
```

恢复过程中锁定对应活动，结束旧的待处理请求，根据数据库库存、已有订单和购买记录重建 Redis；同时更换 epoch。epoch 可以理解成“本轮库存版本号”，旧请求携带旧版本就不能跨过新一轮恢复继续被受理。

Redis 新快照先标记暂停，确认数据库事务已提交后才激活。提交结果不确定或恢复失败时，不贸然开放新抢票，需显式重试恢复。当前一次恢复对请求量有 10,000 条上限，超过会拒绝，不能描述成已实现任意规模自动重建。

## 九、怎么检查库存没有出错

MySQL 中一条重要关系是：

```text
可用库存 + 待支付订单数 + 已完成订单数 = 总票额
```

取消、过期订单已经释放名额，不计入占票订单数。这是每个票档的数据库关系，不是要求 Redis 与 MySQL 在异步处理中瞬时相等。

还要检查：成功请求必须有订单，非成功请求不能有订单；重复执行不改变库存；后台未完成动作、待核对预占不能持续积压。

现有测试包括百张票并发竞争、重复消费、取消幂等、订单写入失败回滚、补偿与迟到受理竞争、旧 epoch 被拒绝、Redis 状态缺失时拒绝新预占。本文整理未重新执行测试。

## 十、面试时可以直接这样讲

校园抢票的票额有限，所以我先用 Redis Lua 在一次执行中校验库存和用户资格，并预扣名额。同一次操作重试时复用请求标识，不重复预扣；不同请求也不能绕过同一用户的购买限制。

Redis 预扣只是前置预占，正式建单仍由 MySQL 条件扣减和唯一约束保护。库存扣减、订单创建、请求结果和后续 Redis 动作放在一个数据库事务中，失败一起回滚。

因为 Redis 和 MySQL 不是一个事务，我额外处理两段故障：预占后请求没存下来，后台根据待检查记录核对数据库，先确定过期结果再释放，阻止迟到请求继续建单；数据库已经提交但 Redis 没更新，则靠持久化动作重试。

库存恢复按业务状态区分，建单成功只确认预占，取消或过期才归还票额，并保留当前规则要求的购买限制。应用重启后继续未完成任务；Redis 数据丢失则需要显式恢复和 epoch 隔离，不会盲目重置库存。

## 十一、常见追问

**Redis 没票，但 MySQL 还有票，是不是一定出错？** 不一定，可能有尚未建单的预占；要看请求状态和补偿任务，不能直接把 Redis 改成 MySQL 的数。

**有 Lua 为什么还要唯一索引？** Lua 保护 Redis 预占，数据库仍需独立防御消息重复、恢复过程和不同路径的重复建单。

**为什么保留取消用户的购买限制？** 这是当前每人每票档限购一次的业务规则。若要支持取消后重买，需要重新设计资格、历史订单约束和补偿逻辑，不是简单删除 Redis 用户字段。

**补偿一定能马上完成吗？** 不能。依赖恢复后可以重试；永久故障、积压、异常状态仍需要观测和管理处理，不能承诺没有前提的“最终一定成功”。
