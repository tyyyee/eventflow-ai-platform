## 定稿条目

**订单查询分库分表：** 基于 ShardingSphere-JDBC 按用户路由历史订单读模型，落地双查询库、32 张分表；保留交易库本地事务，通过持久化同步任务、版本幂等与差异补偿实现状态同步，支持断点回填、核对切换及故障回退；完成万级迁移、百万级合成数据查询对照和真实登录业务联调。

新增在原有多级缓存、库存一致性、异步建单、延迟关单四条之后。原四条设计与指标保持各自证据范围，不将查询分片写成秒杀吞吐提升。

## 面试中的准确范围

- 项目总计一个交易源实例、两个历史查询实例。原交易订单不迁出，原同库 32 表投影也保留。
- 默认仍使用本地查询；启用可选构建及配置后，才向新实例同步。切换前检查回填、同步和核对，故障时可只连接源库切回本地查询。
- 1 万条为独立源库中的合法历史订单 fixture，用于回填、断点继续、并发更新、版本和完整核对。
- 10 万和 100 万条为独立基准 schema 中的合成历史记录，用于单表、同库分表、跨实例分片的查询对照，不是实际用户订单或真实下单流量。
- 性能对照测量 JDBC 层列表与计数，每模式并发 8、三轮各 3 秒，包含客户端校验和路由开销，不包含 HTTP、Cookie 会话鉴权及实际入口的控制状态读取。
- 后续完整联调使用真实注册账户、Cookie 和 CSRF，验证源库交易、Kafka 异步建单和分片历史查询；登录后的 HTTP 对照另有三轮记录，使用少量实际接口创建的测试订单、有意控制请求节奏。不能把这组 HTTP 结果说成百万数据下的接口容量。
- 查询库停止时选择 SHARDED 会返回 503；切回 LOCAL 后继续交易，目标恢复后补齐变更。Kafka 中断与后端重启后，已受理的 Outbox 请求恢复建单；Redis 恢复窗口使用同请求键重试。故障阶段的预期 503 与稳定对照中的错误率分别记录。
- 小规模下跨实例有额外成本，百万普通用户查询观察到改善，热点用户混合负载收益有限，轮次波动明显。不写“分片必然提速”“整站吞吐翻倍”或生产容量。
- 没有实现分片自动扩缩容、实例主从容灾或主交易分库。没有改为雪花 ID，没有修改库存、支付、关单或多级缓存实现。
