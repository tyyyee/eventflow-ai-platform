## 简历正文

**趣票｜校园文体活动抢票平台**

面向校园音乐节、赛事、讲座等活动，提供活动浏览、限时抢票、候补补位、订单查询、模拟支付与超时关单。技术栈：Spring Boot、MySQL、Redis、Caffeine、Kafka、ShardingSphere-JDBC。

- **多级缓存：** 基于 Caffeine 和 Redis 实现多级缓存，结合 Bloom Filter 过滤无效 ID；缓存软过期时短暂返回旧数据，由单个请求持锁重建，Redis 异常时限制数据库回源，降低热点查询对数据库的压力。
- **库存一致性：** 基于 Redis Lua 实现票额预占与一人一票档校验，MySQL 通过条件扣减及持久占用记录裁决库存；针对库存与订单跨库，引入幂等占用和持久补偿任务，支持提交中断、取消、超时及服务重启后的恢复。
- **异步建单：** 在用户分片内同事务写入请求与 Outbox，基于 RocketMQ 异步建单，通过发送重试、消费幂等及提交后确认处理重复消息和进程中断，保障已受理请求可恢复、订单不重复。
- **延迟关单与并发控制：** 基于 RocketMQ 延迟消息和分片内持久任务实现超时关单，通过同请求锁与 CAS 条件更新协调支付和关单；结合幂等库存回补及退款任务处理遗漏关单、重复通知与关单后付款。
- **核心业务分库分表：** 基于 ShardingSphere-JDBC 按 user_id 将主订单及关联交易表拆分至4库×8表，通过绑定表与带分片键查询减少跨库访问，结合带 worker 租约的 Snowflake 和订单定位目录支持全局ID及非分片键查询；实现增量镜像、断点回填、字段核对与维护切换回退。

## 分库分表单条精简版

**分库分表：** 基于 ShardingSphere-JDBC 按 user_id 实现主订单及交易任务4库×8表拆分，通过绑定表、Snowflake 与订单定位目录支持用户交易路由和订单号查询；结合增量镜像、版本校验及反向回填完成迁移与维护切换回退。

## 面试时解释的动机与边界

动机是为订单持续增长和多用户并发验证水平拆分，降低订单在单表、单实例上的集中程度。项目实际数据量仍较小，没有经历线上千万订单瓶颈；不能编造业务增长和迁移规模。

主订单、请求、Outbox、支付、关单任务按用户共置；登录凭据、活动库存、全局定位与模拟渠道幂等账本仍在源实例。跨库库存与订单依靠持久占用和幂等补偿收敛，不能说它们仍是一个本地事务。小型展示配置广播，动态库存不广播。单活动库存热点、源库单点、主从自动容灾和任意在线扩容尚未解决。

迁移是源事务日志驱动的异步镜像，最终维护停写切换，支持断点继续；不是业务线程同步双写两个库，也没有零停机灰度。切换后回退必须反向回填最新主数据，不能只切开关。

## 数字使用规则

不添加主分片吞吐提升、亿级容量或线上可用性数字。真实中间件功能测试、故障恢复和少量订单HTTP采样的结果均见[本轮记录](../verification/2026-10-27-core32/README.md)，它们说明已验证的行为，不代表生产容量。

后续补做的[主交易容量复核](../verification/2026-10-27-core32-capacity/README.md)实际写入100万条合成主订单，32片各31,250条，完成连接上限及单分库导出恢复验证。该轮同机等资源下的实际CORE32查询、分散写入均未快于单库，不能改写成吞吐收益。若补数字，可写“完成百万条合成主订单的分片路由与单分库恢复验证”，并说明SQL层和合成数据条件。

缓存数字仍属于历史实验：在同机、正常登录、32并发、20个商家基础信息条目均匀查询的四轮A/B中，P95中位数12.852→10.856ms，成功吞吐中位数4605→5812 req/s。详见[2026-10-05缓存实验](../verification/2026-10-05-cache-matrix/README.md)。没有重跑为本轮分片构建下完整活动接口的结果。聊天中的13.85→10.85ms、4204→5396 req/s未定位到对应留存记录，不拼接使用。

此前1万迁移、百万行JDBC和8942次HTTP对照均属于旧历史读模型；不能搬到本轮主订单分库条目。旧实验本身保留在各自日期目录。

这里“此前百万行”指旧历史读模型实验；新增百万主订单实验另有独立schema和上述容量复核记录，两者不合并为迁移规模或完整秒杀容量。
