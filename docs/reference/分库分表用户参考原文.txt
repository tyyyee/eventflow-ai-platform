为什么需要分库分表
原版黑马点评采用单库单表架构：应用层只配置了一个MySQL数据源，所有业务表都放在同一个库中（例如tb_user、tb_shop、tb_voucher_order等）。这种架构在起步阶段简单易用，但业务增长后会出现明显瓶颈。

问题1：连接数与并发瓶颈
单实例MySQL连接数有上限，秒杀、签到、下单等高并发场景会把连接池打满，导致请求排队甚至失败。

问题2：单表膨胀导致索引与SQL变慢
单表行数持续增长，B+树层级增加，随机IO成本上升。经验上单表超过数百万行或数GB时，查询性能开始明显下降。

问题3：写入热点与锁竞争
tb_voucher_order、tb_user_sign等写入热点表在高并发下集中写入，单库写入能力成为瓶颈，锁竞争明显。

问题4：容量与可用性风险
单库磁盘容量有限，备份恢复窗口长；数据库出现故障会影响全站核心业务。

问题5：扩展成本高
单库只能纵向扩容（升配），成本高且有上限，无法满足长期增长。

因此，引入分库分表是点评在高并发与持续增长场景下的必然选择。

什么是分库分表
把原来集中在一个库或一张表的数据拆分到多个库、多个表，并通过路由规则让业务看起来还是一张表。

拆分方式有什么
分为垂直和水平方式，按照具体拆分方式不同。这也是个经典八股，我在实习/秋招问到分库分表都遇到过

垂直分库
1. **（按业务拆）**把用户、订单、优惠券等不同业务拆到不同库，降低库的耦合与负载。
2. **（按字段拆）**把高频字段和低频字段拆开，减少主表行宽，提高缓存命中率。
  
水平分库
1. **（按分片键拆库）**同一张表的数据按分片键拆到不同数据库中，提升容量与并发。
2. **（按分片键拆表）**同一数据库中按分片键拆成多张表，降低单表规模。
  
路由过程
以哈希取模为例，路由过程如下：
[图片]
示例：dbCount=4，tablePerDb=8，user_id=10086，hash函数假设为其本身（方便演示）

设系统采用分库分表策略，参数为 dbCount = 4、tablePerDb = 8，总分片数为 32。以 user_id 作为分片键，为便于说明，假设哈希函数为恒等映射，即 hash(user_id) = user_id。

当请求 user_id = 10086 时，首先计算逻辑分片号：
shard = hash(10086) % 32 = 10086 % 32 = 6

该结果表示数据落在第 6 号逻辑分片（全局分片编号范围为 0～31）。
随后根据逻辑分片号确定数据库索引：
dbIndex = shard / tablePerDb = 6 / 8 = 0

因此，该数据位于第 0 个数据库（db0）。在该配置下，逻辑分片与数据库的映射关系为：
shard 0～7 → db0，8～15 → db1，16～23 → db2，24～31 → db3。

最后确定具体的物理表：
tableIndex = shard % tablePerDb = 6 % 8 = 6

即落在第 6 张分表 tb_user_6。
综上，user_id = 10086 的最终路由结果为：db0.tb_user_6

拆分思路：
目标是在分库分表后尽量保证请求单库、单分片可完成，避免引入不必要的分布式 Join 和跨库事务开销。

首先，对于分片表，选择的对象均具备三个共同特征：数据规模增长快、写入并发高、且查询通常带有明确的业务主键。这类表如果长期集中在单库单表中，容易成为系统的性能瓶颈。因此在拆分时，统一选择具备高区分度、且在查询条件中天然存在的字段作为分片键。例如，用户表及其衍生行为表（如签到记录、优惠券订单）几乎所有核心查询都围绕 user_id 展开，以 user_id 作为分片键可以保证用户维度的读写请求稳定落在同一分片内，从而提升查询性能并降低路由复杂度。对于对账类日志表，则以 order_no 作为分片键，以匹配对账场景中“按订单号精确定位”的访问特征。

其次，对于广播表，其共同特点是数据规模相对较小、更新频率低，但在业务中被频繁引用。例如商户基础信息、商户类型和优惠券配置等数据，几乎会被订单、查询和展示类接口反复使用。如果将这类表也进行分片，反而会在查询时引入跨库访问和额外的路由成本。因此在实际设计中，将其作为广播表，在每个分库中保留一份完整副本，使得涉及商户或优惠券信息的查询可以在本地数据库内完成，避免跨库访问，提升整体查询效率。

最后，对于绑定表的设计，其核心目标是规避分库分表后最常见的性能陷阱——跨分片 Join。在用户相关的业务链路中，用户表、签到表以及订单表之间存在高频的关联查询关系。如果这些表采用不同的分片键或路由规则，将导致一次业务查询需要访问多个分片，严重影响性能和系统复杂度。因此在拆分规划阶段，明确将存在强关联关系的表按照同一分片键进行绑定，保证它们在物理存储层面具备一致的路由结果，从而使用户维度的查询和统计操作能够在单个分片内完成。

有人会问为什么商户表也算广播表，广播表和分片表不是绝对分类，而是对当前业务阶段下数据访问模式和成本收益的判断结果 。我包装的时候写的是区域性的本地生活平台，单一城市级别场景，即使覆盖全城商户，数量通常是几万到十几万量级，而不是千万级、亿级，其次这张表表结构相对窄， tb_shop 主要是基础信息（名称、地址、经纬度、评分等），字段数量有限，行宽不大，对存储和查询压力相对温和，商户信息主要是后台维护，线上请求以查询为主，非常适合做缓存和本地化访问。大多数业务并不是“我要查一批商户”，而是：查订单 → 展示商户信息 / 查优惠券 → 展示所属商户 / 查商户详情 → 精确 by shop_id，这种访问模式下，广播表能显著减少跨库访问成本。所以在当前规模 + 当前业务模式下，把 tb_shop 视为广播表是合理的。

三、分片策略

3.1 分片算法
采用哈希取模，即根据分片键计算逻辑分片号，再映射到具体的数据库和物理表

哈希取模能够较好地保证数据在各分片之间的均匀分布，避免因顺序写入或业务热点导致的单分片压力过高问题，尤其适用于以 user_id 为核心访问维度的业务场景。其次，该策略能够保证同一用户相关的数据稳定路由至同一分片，有利于用户维度的查询与统计操作，配合绑定表设计，可以在大多数核心业务请求中避免跨分片访问。

不过需要注意的是，哈希取模分片算法属于静态分片策略，在分片数量发生变化时会引入数据重分布成本。因此，在当前阶段通过合理规划分片规模来降低短期内扩容的必要性。

3.2 分片规模
4库 × 8表 = 32分片
单表数据量控制在数百万级以内，通常能够在索引合理的情况下维持稳定的读写性能。

按单表可承载约 500 万行数据估算，32 个分片的理论数据容量可达约 1.6 亿行，能够覆盖平台在中期阶段内的用户行为数据和订单数据增长需求。

3.3 为什么不采用一致性哈希 / Range 分片
一致性哈希的主要优势在于分片节点变动时的数据迁移成本较低，适用于节点频繁扩缩容或需要高度弹性伸缩的分布式系统。然而在本项目中，数据库分片数量在中期内相对稳定，短期内不存在频繁扩容需求。一致性哈希需要引入虚拟节点、维护哈希环，并在路由和运维层面增加复杂度，其带来的收益在当前阶段难以覆盖额外的实现与维护成本。因此，未作为优先选择。

Range 分片通常按照时间或连续 ID 区间对数据进行划分，适合以时间序列为主、且查询以范围扫描为核心的业务场景。但在本系统中，核心访问路径以用户维度的精确查询为主，若采用 Range 分片，容易导致新数据集中写入到少数分片，形成写热点，同时在用户相关查询中增加跨分片访问概率，不利于系统整体性能的稳定性。

3.4 补充介绍两种常用的分片策略
**一致性哈希：**是一种将数据和节点同时映射到同一哈希环上的分片策略。每个数据项根据哈希值在环上顺时针找到最近的节点进行存储。当节点数量发生变化（如新增或下线分片）时，只会影响该节点在哈希环上相邻的一小部分数据，从而显著降低整体数据迁移成本。为了缓解节点负载不均的问题，工程实践中通常会引入虚拟节点，将同一物理节点映射为多个逻辑节点以提升数据分布的均衡性。该策略适用于需要频繁扩缩容、对弹性要求较高的分布式系统，但实现和运维复杂度相对较高。

**Range 分片：**按照某个有序字段（如时间戳或自增 ID）的取值范围对数据进行划分，不同区间的数据存储在不同分片中。该策略的优势在于天然支持范围查询和顺序扫描，常用于日志、时间序列或按时间归档的数据场景。然而，Range 分片容易产生写入热点，尤其在新数据持续写入的情况下，最新分片会承受更高的写压力；同时，当查询条件不以范围字段为主时，也可能引入跨分片访问的问题。因此，其适用性高度依赖具体的业务访问模式。

总结

分库分表在实际业务开发是个常见的方案，但目前也有些公司用TiDB/doris/自研组件这样的分布式数据库/数据仓库，他们是自带分库分表的，也不需要解决手动分库分表引入的各种问题，直接一步到位

所以当你的点评考虑引入分库分表的时候，在面试前你一定要准备好这么些问题

1. 为什么要引入 2. 引入后的拆分规划、分片策略 3.引入之后需不需要引入分布式ID 4.怎么做数据迁移
  
听起来可能对实习/校招面试难度有点要求，但其实都不难，难的就在方案梳理和成本取舍

所以针对自己包装的场景，需要准备一套自圆其说的说辞，比如

**在“XX本地生活平台”的业务设定下，引入分库分表并不是一开始就做的技术选择，而是随着业务规模和访问特征变化后的阶段性演进结果。**在项目早期，系统主要面向少量核心用户和商户，整体数据规模和并发压力可控，采用单库单表架构，优先保证开发效率和业务快速迭代。当平台在XX多个区域上线后，用户规模和商户数量持续增长，尤其在餐饮、优惠券秒杀和商户详情查询等场景下，数据库逐渐暴露出性能瓶颈。

**引入分库分表的直接动因主要有三点：**第一，用户表、订单表和优惠券相关表的数据量增长较快，其中用户行为类表（如订单、领取记录）呈现明显的时间累积特征，单表行数迅速膨胀，影响查询和写入性能。第二，核心读请求集中在商户详情页和优惠券列表页，热点数据明显，单库 CPU 与 IO 压力过高。第三，系统已部署为多实例应用，通过负载均衡承接流量，但数据库仍是单点瓶颈，横向扩展能力不足。基于以上问题，在不引入复杂分布式数据库的前提下，项目选择通过分库分表的方式对核心业务数据进行拆分，以较低的改造成本换取可控的扩展能力。

**在拆分规划上，采用“先垂直、后水平”的策略。**首先进行垂直分库，将用户、商户、订单、优惠券等业务拆分到不同数据库中，降低跨业务耦合，避免不同业务的高峰流量相互影响。在此基础上，仅对增长最快、访问最集中的表（如订单表、优惠券领取记录表）进行水平拆分。水平拆分时，以 user_id 作为分片键，将同一用户相关的数据尽量路由到同一分片，减少跨库查询的概率。数据库与表的数量根据当前规模预留扩展空间，目前是4 库 × 8 表，既能满足现阶段需求，也为后续扩容留下余量。

**在引入分库分表后，同步引入分布式 ID 生成方案是必要的。**由于原有数据库自增主键在多库环境下无法保证全局唯一，订单号、优惠券记录等核心业务 ID 需要具备唯一性和趋势递增特征。因此项目采用基于时间戳的分布式 ID 生成策略，在应用层生成 ID，避免数据库成为 ID 分配瓶颈，同时也便于后续日志分析和数据排序。

**关于数据迁移，采取的是“双写 + 灰度切换”的方式。**在分库分表上线前，先完成新库表结构的创建和路由逻辑的开发。迁移阶段，系统同时向旧表和新表写入数据，并通过校验脚本对比关键数据的一致性。待新表数据完整、读写逻辑稳定后，逐步将读流量切换到新分库分表结构，最终下线旧表，完成平滑迁移，避免对线上用户造成影响。

**最后，需要明确的是，引入分库分表并非“技术最优解”，而是“阶段最优解”。**相较于 TiDB、Doris 等分布式数据库方案，手动分库分表增加了开发复杂度和运维成本，但在中等规模业务下，能够以较低的引入成本获得明确的性能收益，也更有利于开发者理解系统瓶颈与数据访问特征。因此，在当前的XX本地生活场景下，该方案在复杂度、性能和可控性之间取得了相对平衡。
