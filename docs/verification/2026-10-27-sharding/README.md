## 已发现并修复的验收问题

首次 1 万条验收工具使用 DriverManagerDataSource 逐查询建立连接，在 Windows 上耗尽临时 TCP 端口，未通过。失败日志保存在本地忽略目录 .local/failures/01-volume-connection-churn.*。后续改用与应用相同的有界连接池，未更改宿主机网络参数。只有重跑通过才计入规模验收。

首次查询对照的 36 轮测量均无失败，但结束时一次删除百万条基准数据触发 5 秒连接超时，整轮判为失败。失败日志、样本及结果另存 .local/failures/02-*。随后改为按已记录实验批次每次最多删除 2,000 行；清理恢复单独通过，再重跑完整 36 轮，测量与清理全部通过。没有提高超时来掩盖无界操作，也没有清空业务库。

运行包检查还发现原 H2 test scope 会漏掉 ShardingSphere 的内部元数据运行依赖，已改为仅在 sharding profile 中使用 runtime scope，并复验运行包与实际维护命令。业务存储始终为真实 MySQL。

## 结果解释与范围

每次测量操作包含一次历史列表和一次总数查询。这里只测 JDBC 层，不包含 HTTP 网络、正常 Cookie 会话和实际入口控制状态查询，不称为秒杀 TPS 或整站容量。
三种模式连接上限总计均为 8；单实例 buffer pool 128 MiB，对照双实例各 64 MiB。单一热点用户仍只访问一个实例。共享宿主机、三秒短轮次、不同布局和客户端路由开销都影响结果，属于本机观察，未做统计显著性或生产流量推断。
10 万条普通用户查询中跨实例开销较明显；100 万条普通用户查询中跨实例表现较好；包含高订单量用户的混合负载收益较小，部分轮次波动明显。不能据此断言小表应该分库或所有查询都会提速。

本轮只验证同机三个独立 MySQL 8.0.31 实例，不代表跨机高可用。Docker 叠加部署仅检查 YAML、DDL 和构建配置一致性，未在本机实际启动；未重跑原 Redis/Kafka 完整联调。缓存、Trading、Payments、DelayedClose 及原 OrderProjection 源码哈希保持不变。

验收以命令实际结果及精简证据为准。未执行的实验不记为通过。
