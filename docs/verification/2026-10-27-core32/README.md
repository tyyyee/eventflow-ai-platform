## 本轮发现并修正的问题

1. ShardingSphere对目标UPDATE中的TIMESTAMPADD表达式出现绑定错误：目标更新改用已计算的时间参数，重新验证退款、租约、关单任务。
2. 初次迁移核对发现前一测试遗留业务档案：增加全局家族行数核对、补齐测试清理，并将直接测试移到独立schema，避免测试混入演示环境。
3. Windows旧后端持有构建JAR，打包重命名失败：停止已确认归属的旧项目后端；新脚本复制带摘要JAR后启动，避免后续打包锁冲突。
4. 本机并行初始化时Redis300ms握手超时：隔离运行参数调整为5秒连接等待、1秒命令等待，未改缓存算法。
5. Snowflake每毫秒序号从0开始与user_id%32组合产生低频热点：新毫秒起始序号分散在0–31，并补趋势性与32片覆盖测试。
6. 实际进程崩溃恢复暴露启动元数据加载超过worker原租期：续租移到独立线程，在Spring调度器启动前持续运行；新增32秒租约回归，并重跑真实JVM故障验收。
7. 旧模式完整回归首轮同样遇到Redis300ms握手超时，导致10项HTTP测试无法加载容器；保留日志，使用相同本机5秒连接/1秒命令参数重跑，不把启动失败计为业务断言通过。

## 结论的适用范围

已实现真实主订单拆分和交易恢复机制。广播只用于小型展示快照；源库库存与订单之间使用多个本地事务及持久补偿，没有分布式原子提交承诺。

不声称四倍吞吐、1.6亿订单容量、零停机灰度、主从自动容灾或无损源库单键回退。恢复/迁移当前每用户每家族或每活动有1万条保护上限，超限需后续分页方案。单活动库存锁、源目录单点、固定取模扩容搬迁成本仍存在。
