## 二 测试数据和判定方式

每个场景创建独立H2测试库，使用项目的迁移脚本和生产查询、工具、运行时实现，不改演示环境的MySQL、Redis或消息队列数据。真实模型批次直接调用DeepSeek官方HTTPS接口，不经过本地示例解析器。供应商模型别名为 `deepseek-flash`，非思考模式，temperature为0，单次最多生成1000 tokens。

基础数据包含9个可购买活动：不同校区和类型、免费讲座、超出预算的活动、明晚与午后活动、周末及后天活动。活动价格为0、20、30、40、50、60、80、150元等已知值；每个活动初始库存100。规划表刻意保存不同的影子价格与库存，用来检查是否读取交易表。订单场景另准备当前用户和另一个用户的请求及订单。

日期使用上海时区，以每个场景记录的 `anchorTomorrow` 为准；不是固定冻结的系统时钟。价格变化、售罄等场景由测试程序在明确的两轮之间修改测试库，并按修改后的事实核对。

自动判定包括以下内容：

1. 工具轨迹包含业务需要的工具；售罄找替代时，查详情先于搜索替代。
2. 返回的活动价格、库存和来源与隔离数据一致，日期、预算、校区和类别满足用户条件。
3. 修改一项条件后，其他明确条件仍保留；清空条件必须由用户提出。
4. 订单只属于当前用户，已受理不误报建单，关闭不误报退款。
5. 需要拒绝的场景按拒绝结果判定，不能要求全部任务都返回SUCCEEDED。
6. 重复key、非法参数、异常工具和中断恢复有明确预期，不仅检查HTTP状态。

允许合理的工具路径差异，不要求每次返回相同JSON文本。测试没有使用付费LLM-as-Judge，也没有自动评价措辞是否优美。

## 三 真实评测发现的问题

### A06 没有匹配时擅自放宽类别

用户要求“明天、主校区、预算1元、音乐活动”。第一次搜索正确返回空集，模型随后把 `category` 和 `query` 清空，找到了免费讲座，原实现又将任务标记为成功。

这说明“有数据来源”和“查询成功”并不能证明回答满足用户要求。修复后，首个有效搜索的条件保存在本轮检查点中；同一轮后续搜索不能改变这些约束，违规请求由工具拒绝。下一轮用户明确修改条件时，使用新检查点，可以正常调整或清除。提示词也明确无结果时停止，不自行更换类别、预算或校区。

这层保护防止同一轮看到结果后再偷偷改条件；不能保证模型第一次就提取对全部条件，所以仍保留独立的参数及返回内容断言。

### A09 查询订单详情覆盖了列表

模型先查到本人两条记录，又逐笔读取详情。原实现每次详情查询直接覆盖 `cp.orders`，导致最终只展示最后一条。

修复后，同一轮的订单结果按 `requestId` 合并，详情只更新对应记录，保留其他已查到的本人订单。提示词同时要求列表信息足够时停止，避免无必要的详情调用。只有详情查询的单轮仍正常返回该笔记录。

### B09 补查规则隐藏了替代活动

模型先确认活动售罄，再搜索到符合原条件的替代活动，但之后又查询规则。原输出逻辑只根据最后的RULES类型显示规则，替代活动卡片消失。

修复后，补充规则时保留本轮已查到的活动卡片和来源，不因为后一个工具结果隐藏前面的有效活动。混合结果使用可见事实中最早的查询时间，避免将旧库存快照标成最新查询。提示词也限制未被请求且不必要的规则调用。

三处修复分别新增确定性回归测试，没有删除原先失败的业务断言，也没有将失败用例移出测试集。`summary.json` 会检查修前修后场景源码哈希和ID列表一致。

## 四 新增验收场景

修复完成后新增以下8个场景，执行前未用这些输入调试提示词；执行过程中未再修改模型规则。

| ID | 场景 | 核心判定 |
| --- | --- | --- |
| H01 | “明晚、最多六十块” | 中文金额转6000分，保留晚间与主校区 |
| H02 | “还是回主校区，钱和时间别动” | 只变更校区 |
| H03 | “不限定哪个校区了” | 清除校区，其他条件保留 |
| H04 | 19:00至21:00、80元 | 时间上下界和预算正确 |
| H05 | 免费音乐活动但库中没有 | 返回无匹配，不用免费讲座替代 |
| H06 | 已展示活动涨价 | 重新读取9000分，并提醒超出原80元预算 |
| H07 | 陌生请求编号属于其他用户 | 归属校验拒绝，不返回对方订单 |
| H08 | “不是让我买票，看看抢票进展” | 不误拒绝为自动购票，返回本人记录 |

八个场景全部通过。它们仍是开发者人工编写的小样本，没有外部盲测或线上用户数据，后续如果用于调试，就应另建新的独立验收集。

## 五 费用和执行限制

三批真实模型验证共158次调用，供应商报告总计306439 tokens，没有用量未知调用。本轮不含此前五轮冒烟的21507 tokens。

将所有已报告tokens都按8元/百万tokens计入，保守估算为2.451512元；这不是实际账单。账户余额从首批前的9.92元，到新增验收批次后显示9.69元，最终于上海时间15:54:55查询显示9.65元，见[最终余额记录](final-balance.json)。余额存在显示精度和结算延迟，不能把差额当成逐批准确费用。

评测器只允许Flash模型，每批最多90次模型调用；按已报告用量和下一次调用的预留量，在2.5元的保守估算阈值前停止继续调用。供应商结果或用量未知时停止剩余真实模型场景，并记录NOT_RUN_BUDGET，而不伪装通过。预检还要求账户至少剩余3元。

这些限制是评测批次的停止策略，不是生产环境的精确人民币全局硬限额。运行时原有每轮60秒、5次决策、8次工具调度和token限制继续生效。

## 六 怎样复现

在项目根目录使用PowerShell 7。依赖为Java17、缓存中的Maven3.9.9及已有项目依赖；H2与JUnit均复用现有依赖。

不付费回归：

```powershell
./backend/scripts/assistant-evaluate.ps1 -Mode deterministic
```

真实模型验证前，在本机当前进程环境配置 `DEEPSEEK_API_KEY`。脚本不保存或打印密钥。

```powershell
# 20个已知业务场景，会产生API费用
./backend/scripts/assistant-evaluate.ps1 -Mode live

# 只复测指定场景
./backend/scripts/assistant-evaluate.ps1 -Mode live -Cases A06,A09,B09

# 8个新增验收场景，会产生API费用
./backend/scripts/assistant-evaluate.ps1 -Mode holdout
```

默认使用时间戳生成新报告名，也可指定新的 `-Label`。已有结果不覆盖。原始日志在 `.local/assistant`，逐场景JSON保存在本目录。每条记录包含测试数据前后快照、任务、结构化状态、工具参数及结果、错误、耗时和模型调用用量；所有业务数据都是测试生成的数据，不含真实用户记录。

汇总脚本只读取既有结果，不调用模型：

```powershell
node ./backend/scripts/summarize-assistant-evaluation.mjs
```

该脚本针对本轮固定报告名核对结果，可反复运行，不会覆盖原始批次记录。

## 七 验收范围

真实模型评测使用H2隔离数据，因此不代替MySQL方言、真实Redis预占、RocketMQ建单或CORE32跨库验证。两项真实中间件联调单独覆盖原建单结果的助手查询。本轮没有重新执行四库助手端到端或性能压测。

本地40场景中的C10具体检查“模型自由文本不能冒充付款或价格事实”，不是完整的间接提示注入攻防评测；未知工具、伪造身份、候选ID和业务写入由其他场景分别验证。

修前85%和修后100%只能描述同一组20个已知场景的结果。不能据此宣称真实用户准确率100%，也不将场景整体耗时混成接口P95。当前没有自动化语言风格评分、线上用户满意度或大规模公开基准成绩。

演示数据的活动限购文案同步统一为“同一用户对同一活动”，与平台规则保持一致；没有引入票档模型。

## 八 面试怎么讲

可以这样介绍：

> 我把评测分成运行机制和模型业务效果两部分。权限、幂等和中断恢复主要用40个确定性场景回归；真实模型用20个单轮及多轮场景检查工具、条件和最终业务数据。第一轮发现3个问题，分别是无结果后放宽条件、订单详情覆盖列表、规则查询隐藏活动卡片。补充后端约束和结果合并后，同一组20个场景全部通过，再用8个未参与调试的新场景单独检查。每个case保存数据、轨迹、断言结果和用量，不把接口成功当成任务成功。
