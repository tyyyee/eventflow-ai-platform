# 主交易分片：五项目标的合成数据复核

针对“连接并发、单表增长、集中写入、容量与恢复、长期扩展”补做量化验证。合成的是订单和负载，执行的是实际MySQL、实际ShardingSphere和实际导出恢复，没有模拟耗时或预设收益。

**结论：五项目标没有全部完成。** 已验证连接承载可分散、主订单表规模可拆分及单分库恢复；当前同机实测尚未取得实际分片链路的查询/写入吞吐提升，主从容灾与在线扩容未实现。

## 逐项目标结论

| 目标 | 本次证据 | 完成程度 |
|---|---|---|
| 连接数与并发瓶颈 | 每实例max_connections=40，单实例45次连接尝试成功40次、5次返回1040；四实例分担45个连接全部成功 | 已验证连接承载分散；不等于已提升整条抢票链路TPS，源目录/库存仍有单点限制 |
| 单表增长 | 实际主订单100万条拆到32表，每张31,250条、每数据库250,000条，错片0；单表和分表查询均使用索引 | 已验证体量控制；没有验证出“百万行必慢”的阈值，当前实际分片查询尚未更快 |
| 集中写入与锁竞争 | 32并发分散用户持久化：单库1803.9次/秒，实际四库1442.8次/秒；热点用户仍只落同一片 | 写入位置已分散，吞吐提升未达到；单用户热点和源活动库存锁仍需分别治理 |
| 容量与备份恢复 | 百万级单订单表与一个分库的8张订单表均实际导出并恢复，逐字段差异0；恢复单元约降到1/4数据量 | 已验证拆分存储与单分库恢复；没有主从/自动切换，不能说高可用目标已完成 |
| 水平扩展 | 四个独立实例路由与固定32片维护迁移已经验收 | 具备多实例布局及维护迁移；尚无在线增加分片、自动搬迁和弹性扩缩容 |

## 公平条件与测试边界

- 在独立`qupiao_core_capacity` schema进行，源目录库、真实演示订单、旧验证schema不参与造数。
- 先10万、后100万主订单；4096个合成用户，用户分布均匀，主订单字段和索引沿用当前cx_order。
- 大规模历史基数只填主订单表，不伪称100万条完整抢票流水。新增写入采样实际提交请求、Outbox、订单和close任务。
- 三种路径：单库普通JDBC、当前CORE32逻辑表ShardingSphere、四库直接物理路由。直接路由用于分析中间件开销，不作为项目接口性能。
- 各模式总连接预算24；单库缓冲池256MiB，四库各64MiB、合计256MiB。测试后源实例恢复原128MiB，演示后端恢复运行。
- 所有数据库和客户端在同一台Windows主机、共享CPU和磁盘。四个进程不能视为四台独立硬件。硬件与参数见[environment.json](environment.json)。
- 每组3轮、每轮4秒，轮换模式顺序；并发16/64查询，32并发写入。报告分别取三轮QPS与P95中位数，不混成同一轮。
- 这是SQL/JDBC对照，不含源库存裁决、Redis、Kafka、HTTP鉴权和完整补偿链路；不能用作完整抢票TPS。
- 连接上限测试另行停止应用与基准连接池，再保持真实连接。它增加实例数与总服务端连接容量，与等总资源性能对照分别解释。

## 主要结果

| 场景 | 单库单表 | 实际四库CORE32 | 结论 |
|---|---|---|---|
| 百万订单、16并发查询 | 10069.3次/秒，P95 2.31ms | 6296.1次/秒，P95 3.74ms | 当前同机分片链路更慢 |
| 百万订单、64并发查询 | 8815.1次/秒，P95 10.58ms | 5763.5次/秒，P95 49.80ms | 当前同机分片链路更慢 |
| 百万基数、32并发分散写入 | 1803.9次/秒，P95 49.02ms | 1442.8次/秒，P95 77.62ms | 未取得写入提升 |

百万订单16并发的四库直接路由诊断为11983.2次/秒、P95 2.24ms，说明物理拆分路径与中间件路径存在开销差异，不能把该数字当作现有CORE32接口收益。也不能据一次同机实验推断换成四台机器后的结果。

完整[54轮对照表](benchmark-table.md)、[逐轮数据](benchmark.json)和[聚合摘要](summary.json)保留所有结果，共1,674,415次尝试、77次连接/事务开启失败：单库10次，直接路由诊断67次，实际CORE32路径0次。大部分失败发生在热点用户场景，连接等待、锁竞争和各轮耗时波动均保留；“基准测试程序通过”不表示每次负载操作都成功。

新写入最终核对：单库28,763条请求、28,763条Outbox、28,759条订单；四库合计41,774条请求、41,774条Outbox、41,768条订单。过载下有4/6个请求停留在首段提交后、订单阶段未成功，作为基准数据保留；成功终态缺订单的差异为0。此处没有启动消费和恢复任务，不宣称已经排空全部模拟Outbox。

## 存储与恢复

百万条种子订单：单表数据和索引分配页约283.31MiB；四库订单表合计约370.50MiB；每张分表约11.58MiB。分片控制的是每表/每节点体量，额外的表与索引开销会使总空间增加。统计不是文件系统物理占用，详见原始字段。

在写入采样完成后停止演示后端，导出与恢复结果如下：

| 恢复单元 | 实际订单数 | SQL备份字节 | 导出秒 | 恢复秒 | 逐字段差异 |
|---|---|---|---|---|---|
| 单库订单表 | 1,028,759 | 118,559,250 | 2.82 | 42.56 | 0 |
| 四库中的一个库，8张订单表 | 258,272 | 29,789,650 | 0.40 | 5.06 | 0 |

源/恢复表逐行关联核对ID及用户、请求、活动、金额、状态、创建/截止时间，并对比行数。备份文件与恢复schema见[storage-recovery.json](storage-recovery.json)，SQL留在忽略目录`.local/core32-capacity`。该演练只恢复主订单表，不代表整套交易系统恢复、源目录容灾或自动主从切换；恢复数据量与各实例内存不同，不能把耗时比值作为同等数据恢复提速倍数。

## 复现

已有本项目隔离实例、Java17、Maven3.9.9及MySQL8.0.31后，在项目根目录依次执行：

```powershell
# 首次可不传ResetSyntheticData；重跑时此开关只清理5个实例中固定的容量测试schema。
./backend/scripts/core32-capacity.ps1 -ResetSyntheticData
./backend/scripts/core32-capacity-storage.ps1
node backend/scripts/core32-capacity-report.mjs
```

两套脚本会停止并恢复本项目演示后端，不与HTTP故障验收并行；数据文件和逐次延迟CSV留在`.local/core32-capacity`。不删除业务schema或既有演示订单。首次导出脚本曾因PowerShell单元素数组拆参失败，已改为显式string数组并重新执行，最终结果来自完整成功的第二轮导出恢复。

此前真实Redis/Kafka/HTTP、库存并发、进程崩溃恢复和维护迁移的证据继续见[CORE32功能验收](../2026-10-27-core32/README.md)，与本次SQL容量对照分开引用。
